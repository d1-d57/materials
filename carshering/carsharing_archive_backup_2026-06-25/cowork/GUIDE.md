# GUIDE — методология петли Cowork ↔ Cladkod

> **КОГДА читать:** когда пишешь заход для Cladkod, принимаешь его отчёт или консолидируешь доки. · **ЧТО сюда дописывать:**
> только методологию петли (правила заходов/приёмки/консолидации). · **КУДА дальше:** скелет захода ниже → `briefs/`.

Cowork не пишет код. Он делает три вещи: **пишет заходы**, **судит отчёты**, **консолидирует**. Cladkod стартует с чистым контекстом каждый раз → всё durable живёт в репозитории, а не в памяти. Отсюда единственный принцип: **состояние — в репозитории, а не в сессии.**

## 1. Заход — дай агенту всё заранее

- Заход **самодостаточен**: где код (папка + точка отката), что прочитать поимённо, что сделать, границы, как отчитаться. Агент видит только текст захода.
- **Один заход = одна задача.** Чистый старт бьёт длинную мутную сессию.
- Дай существующие имена/конвенции авансом → агент переиспользует, а не плодит своё. Числа — отсылай к `../data_sources.md`.
- **Критерий готовности — ПРОВЕРЯЕМОЕ условие**, которое может провалиться («оракул печатает X; xlsx пересобран; `check_docs` зелёный»), не «я закончу».
- Заход **двигает/удаляет/переименовывает файлы или сжимает доки** → встрой блок **свежего верификатора** как гейт (см. ниже).

## 2. Приёмка отчёта — суди по отчёту, но проверь гейты

Отчёт (`reports/`) рассчитан на приёмку без построчной сверки. «Принять» ≠ «поверить на слово» — пройди гейты:
критерий готовности выполнен · числа сходятся с `../data_sources.md` · границы соблюдены · решения обоснованы · вынесенное на ревью разобрано. Вердикт: принять ИЛИ вернуть на точечную дочистку. Ответы на вопросы агента идут в начало СЛЕДУЮЩЕГО захода.

## 3. Консолидация — сначала прочитать журнал ЦЕЛИКОМ

Срабатывает на «сведём / наведём порядок / перенесём из истории». Протокол по порядку:
1. **Прочитать `../provenance/journal.md` целиком** до прошлой записи-консолидации (не верхушку).
2. **Выловить каждое осевшее** решение/число/задачу за цикл.
3. **Сверить против домов** (`../README.md §3`) — уже там или нет.
4. **Разложить по домам:** число → `../data_sources.md`; принцип → `../PRINCIPLES.md`; задача → `../PLAN.md`; нарратив остаётся в `journal.md`.
5. **Обновить индекс** (`../README.md §2`) под реальность; `check_docs` зелёный.
6. **Не плодить документы** — дописывать в существующие дома.

## 4. Не плоди документы

Прежде чем завести файл — найди дом в `../README.md §3`. Заводи новый только если ни один дом не подходит, и сразу регистрируй в `../README.md §2` (сирот нет).

## Верификатор внутри захода (для перемещений и потерь)

Заход двигает файлы / правит пути → **верификатор ссылок**: каждая ссылка и путь резолвится, битых 0 (проверить программно — `tools/check_docs.py`). Заход сжимает/архивирует → **верификатор полноты**: по каждой операции «исходный смысл → новый дом», список потерь пуст. Ключ: верификатор — ДРУГОЙ субагент и ДРУГОЙ метод (читает оригиналы из точки отката). Повторяющуюся проверку — выносить в `tools/check_docs.py` + (если под git) в CI, не в ручного субагента каждый раз.

## Тип захода задаёт режим

- **Мутирующий** (код/числа): правки по блокам, пересборка + оракул после каждого, отчёт «было→стало».
- **Организационный** (перенос/переименование, порядок папок): содержание не менять; перемещение рвёт ссылки → отдельный заход с верификатором.
- **Аналитический** (только измерение): данные не трогать; предлагать, не применять; решение — владельцу.
- **Один риск за раз:** не сваливай разнородное в один заход (аудит → мутация → сверка — раздельно).

## Скелет захода (меняется только тело §3)

```
# ЗАХОД для Cladkod — ‹КОРОТКОЕ ИМЯ› (один заход до конца)
> Скопировать ВСЁ в новый сеанс. Прикладывать ничего не нужно. Метрика — КАЧЕСТВО.
КОНТЕКСТ. ‹Проект в 1–2 фразы.› Прошлый этап: ‹состояние.› ЦЕЛЬ: ‹что закрыть.› Приёмка — по отчёту.
## 0. ПЕРВЫЙ ХОД. Точка отката; читать ‹доки поимённо›; сверить числа `../data_sources.md`; показать ПЛАН.
## 1. ДИСЦИПЛИНА. Минимальная правка + проверка (оракул); якорные замены (abort при ≠1); сохранять по умолчанию, вопросы — в отчёт.
## 2. ГРАНИЦЫ. ‹Что НЕ трогать.›
## 3. ЗАДАЧА. ‹Конкретная работа.› КРИТЕРИЙ ГОТОВНОСТИ: ‹проверяемое условие.›
## 4. РЕШЕНИЯ ИЗ ПРОШЛОГО. ‹Учесть, не переоткрывать.›
## 5. ОТЧЁТ → `reports/<дата>_<имя>.md`. Что сделал + зачем + как проверил; решения + почему; вынесено владельцу; контроль (числа, пересборка).
## ВЫХОД. ‹Чек-лист: критерий ✓; пересборка/оракул ✓; check_docs зелёный; запись в journal.md.›
```
