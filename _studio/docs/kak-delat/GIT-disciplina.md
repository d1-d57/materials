## 0. 🔴 ЗАКОН, ИЗ КОТОРОГО СЛЕДУЕТ ВСЁ ОСТАЛЬНОЕ

**COWORK НЕ ВЫДАЁТ ВЛАДЕЛЬЦУ SHELL. Только вызовы `python3 _generator/tools/git_zona.py <команда>`.**

Запрещено выдавать в чат: `rm`, `find`, `xargs`, `git rm --cached`, glob-шаблоны (`*.lock`), подстановки `$(...)`, цепочки `&&`, многострочные конструкции — что угодно, что владелец копирует и исполняет своим шеллом.

*Почему это закон, а не стилистика.* Cowork пишет команды в **bash под Linux** (песочница), а исполняются они в **zsh под macOS**. Разница сред ломает их систематически, и каждый раз выглядит как «git опять не работает»:

| Что сломалось | Как | Когда |
|---|---|---|
| `rm -f .git/*.lock` | в zsh несовпавший glob роняет **всю строку** (`no matches found`); уборка не выполнилась, а владелец думал, что выполнилась | 22.07 |
| `cd /sessions/...` | путь песочницы, на машине владельца такого нет → `fatal: not a git repository` | 11.07, снова 22.07 |
| цепочка `... && ... && ...` | обрыв в середине НЕВИДИМ: `&&` молча не идёт дальше, владелец добросовестно говорит «сделал» | 17.07, коммита не было час |
| `xargs -0` / `-r` | BSD и GNU ведут себя по-разному | 21.07 |
| `$(git ls-files …)` | в репо есть пути с пробелами (`kurs leto 2026/**`) — аргумент расщепляется | 17.07 |

🔴 **То же правило — для КОДА, который исполняется у владельца: фикстуры и хуки.** Они гоняются на macOS (BSD-утилиты), а пишутся в Linux-песочнице (GNU). Никаких `touch -d`, `date -d`, `sed -i`, `xargs -r`, `stat -c`, `grep -P` — нужен нетривиальный системный вызов, делай его `python3 -c`, он одинаков везде. *Цена (23.07): в фикстуре `clean` стояло `touch -d '10 minutes ago'`; на macOS BSD-touch этого не понимает, fallback создал файл с текущим временем, лок посчитался свежим — **фикстура остановила здоровый коммит владельца**, оставаясь зелёной у Cowork. Гейт, зелёный у автора и красный у владельца, хуже отсутствующего гейта.* Проверка на портируемость — грепом:
```
grep -nE "touch -d|date -d|sed -i|xargs -r|stat -c|grep -P" _generator/tools/fixtures/*/PROGNAT.sh .githooks/*
```

⇒ **Нужна операция, которой нет в списке команд ниже — не выдавай shell, а добавь подкоманду в `git_zona.py`.** Она кроссплатформенна, покрыта фикстурой и ведёт себя одинаково у всех. Так появились `clean`, `untrack` и `purge`: каждая родилась из shell-строки, которая ломалась у владельца (`purge` — из `rm -- --help`, где ведущий дефис в имени превращает мусор в «флаг»).

## 0б. Инцидент коммита → след появляется САМ (`INCIDENTY.md`)

НЕУСПЕШНЫЙ `commit` — любая причина: песочница, argv-мусор, нет плана, заглушки в сообщениях, чужой лок, недоехавшие пути, упавший push — **сам дописывает строку** в `../../zhurnal/_INFRA-git/INCIDENTY.md` (`дата время · ветка · симптом · → подсказка · статус`). Это класс 4 разбора 23.07: «пиши отчёт о поломках» — правило, которое в чужом чате забывается молча и ничем не краснеет; теперь дневник ведёт сам инструмент — во всех чатах, у всех троих писателей. Держится фикстурой: убрал автозапись — красная.

| Случилось | Что происходит САМО | Твой ход |
|---|---|---|
| `commit` не прошёл | строка уже в `INCIDENTY.md` | руками не дублируй; чинись по подсказке из вывода |
| тот же симптом повторился в тот же день | строка НЕ задваивается (дедуп) | — |
| инцидент разобран | — | урок с ЦЕНОЙ → `ZHURNAL.md`; в строке INCIDENTY статус `→ ZHURNAL` |

`INCIDENTY` — входящая корзина сырых симптомов, `ZHURNAL` — переваренные уроки с ценой. Не сливать: корзину читают при разборе, журнал — при проектировании.

## 0в. Кривой ВХОД падает громко; untracked-мусор снимает `purge`, не shell

Инцидент 23.07: `bootstrap_arka.py --help` принял флаг за имя арки и **молча** создал папку-сироту `_studio/zhurnal/--help/` со скелетом — untracked, и каждый `git_zona.py plan` тянул её в черновик коммита вперемешку с настоящим. Два корня, оба вшиты в код (не в дисциплину):

- **`bootstrap_arka|zahod|lekcia` валидируют имя** (`validate_slug`): имя арки/захода/лекции с ведущим `-`, пустое, с пробелами/слэшами/ведущей точкой — **не слаг** ⇒ `SystemExit` с внятным текстом, на диске НИЧЕГО не создаётся. Флаг, проглоченный как данные, теперь падает громко, а не фабрикует папку. *(Общий по смыслу `validate_slug` намеренно дублируется в трёх скриптах: единый модуль лёг бы вне зоны заходов.)*
- **Untracked-мусор снимает `git_zona.py purge`, а не `rm`.** Имя `--help` начинается с `-`, любой `rm` примет его за флаг (нужен `rm -- --help`) — ровно ловушка §0, и выдавать такое владельцу нельзя. `purge` трогает **ТОЛЬКО untracked** (отслеживаемое — работа, не мусор; проверяется git'ом), без `--yes` показывает, по `--yes` сносит (Python, не shell), из песочницы отказывает с готовой строкой владельцу, неуспех сам пишется в `INCIDENTY`. Цели — явные пути или карантин-список `plan` (untracked с ведущим `-`). Дубль без ведущего дефиса (как `ZAPROS-fable-2-vneshnie.md` из HANDOFF) авто-карантин не ловит — снимают явным путём: `purge --yes -- <путь>`.

`plan`/`check`/`doctor` теперь называют такой мусор **отдельно** от честного «вне git» и в черновик коммита его не кладут: карантин строгий — «компонент имени с ведущим `-`», ноль ложных срабатываний.

## 1. ВЛАДЕЛЬЦУ — одна тропа на частый случай, команды вокруг

**Самый частый случай — «сохрани вот эту зону с вот этим сообщением» — ОДНА команда:**

```

```

Путь к инструменту в ней — **АБСОЛЮТНЫЙ**, поэтому команда работает из ЛЮБОГО каталога: «запустил из `~`, питон не нашёл файл» (два срыва 23.07) закрыт самой формой — при относительном пути инструмент даже не загружается и подсказать ничего не может. Cowork выдаёт её уже собранной: зона и готовое сообщение внутри; ты вставляешь и жмёшь. Шага «впиши сообщение в `.commit-plan`» на этой тропе не существует. Инварианты — те же, что у плана: `add` + pathspec, граница зоны, ожидание чужого лока, сверка по живым файлам.

Остальные команды — на случаи вокруг; из корня репо:


**Не помнишь, какая нужна — запускай `doctor`.** Он называет состояние и следующий шаг.
`commit` сам снимает мёртвый лок перед работой, сам ждёт чужой живой коммит и сам сверяет по живым файлам, что всё доехало.

**Когда «Claude просит закоммитить»:** обычно тебе уже выдали однокомандную тропу (выше) — просто вставь её. Пакет РАЗНЫХ коммитов идёт через план: `doctor` → `plan` → Claude (или ты) правит сообщения `==` в `_studio/.commit-plan` → `commit`. Скрипт сам дождётся чужого коммита, сам сверит по живым файлам, что всё доехало, и покраснеет, если нет.

**Сломалось непонятное — не разбирайся.** Запусти `doctor` и покажи вывод Claude целиком. Вывод самодостаточен (ветка, лок, недоделанные merge/rebase, расхождение с origin, всё вне git) — диагноз ставится без доступа к твоей машине.

**«Не коммитится» почти всегда одно из трёх** (`doctor` называет прямо):

- **лок занят** — рядом идёт чужой коммит. НЕ поломка: `commit` ждёт сам до 90 с. Лок руками не удалять НИКОГДА (снести у работающего git — испортить индекс; из песочницы проверка «жив ли git» слепа).
- **незаконченный merge/rebase** — пока висит, обычный коммит не пройдёт.
- **detached HEAD** — ты не на ветке, коммит потеряется при переключении.

**Мёртвый лок.** Больше не твоя забота: `commit` снимает его сам, а явно — `clean`. Свежий (младше 5 мин) не трогается никогда: там может идти живой чужой коммит, и снести его — испортить индекс. *Цена, ради которой это автоматизировано: замок держал репозиторий закоммитить-неспособным 28 часов (157 путей вне git), а выданная руками команда уборки не сработала дважды — падала на zsh (§0).*

## 2. COWORK (аналитику) — план файлом, не блок в чат

🔴 **COWORK В ПЕСОЧНИЦЕ — НЕ КОММИТЕР. Это закрытая развилка, а не осторожность** (решено 2026-07-22 экспериментом, после трёх отказов за сессию).

**Почему не «просто другая форма коммита».** В песочнице запрещён `unlink` во ВСЁМ монтировании (не только в `.git`). Git при любой записи создаёт временные файлы и потом их удаляет — удалить не может, они остаются минами и блокируют репозиторий для всех троих писателей. Проверено на одноразовом репозитории внутри того же монтирования:

| Что пробовали | Что осталось в `.git` | Годится? |
|---|---|---|
| `commit -- <pathspec>` (канон для host-side) | `next-index-<PID>.lock`, `index.lock`, `HEAD.lock`; следующий git падает `File exists` — PID в контейнере мелкие и переиспользуются | ❌ |
| ОБЫЧНЫЙ `commit` без pathspec | мин меньше, но `HEAD.lock` и `objects/**/tmp_obj_*` остаются ВСЁ РАВНО | ❌ — «другая форма» не лечит |
| `GIT_INDEX_FILE` в `/tmp` | git всё равно кладёт `next-index-*.lock` ВНУТРЬ `.git` | ❌ тупик |

⚠ **Коммит при этом технически СОЗДАЁТСЯ** — поэтому соблазн «ну ведь прошло же» силён, а цену платит следующий, кто упрётся в чужой лок. *Цена 22.07: репозиторий дважды вставал примерно на полчаса; снять лок из песочницы нечем — каждый раз нужен был владелец.*

**Держится механизмом, а не словом:** `git_zona.py` определяет песочницу (репозиторий смонтирован через FUSE) и `commit` / `worktree add|drop` **отказываются работать**, печатая готовую команду владельцу. Чтение (`check`, `plan`, `doctor`, `worktree list`) работает как обычно. *Раньше запрет жил только в тексте — и был нарушён: правило, которое можно нарушить молча, будет нарушено (`../KONSTITUCIYA.md §11`).*

⚠ **Выдавая команду владельцу, подставь путь ЕГО машины.** Путь песочницы (`/sessions/...`) у него не существует — будет `fatal: not a git repository` (инцидент 2026-07-11).

**Ты в `.git` НЕ пишешь** (песочница). Свою зону коммитишь руками владельца, и в типовом случае — ОДНОЙ строкой в чат:

```
python3 /Users/ivanyakovlev/Documents/GitHub/materials/_generator/tools/git_zona.py commit --zone <зона> -m "<что и зачем>" --push
```

Сообщение пишешь **ты** — прямо в команде: контекст у тебя, владелец ничего не дописывает и никаких файлов не правит. Путь к инструменту — АБСОЛЮТНЫЙ путь машины владельца (не песочницы!): тогда команде безразлично, из какого каталога её запустят — два срыва 23.07 были ровно про запуск из `~`. Плейсхолдеров не оставлять: сообщение с `<...>` инструмент отвергнет. Проверить команду из песочницы можно ей самой: она откажет по песочнице и напечатает готовую строку владельцу.

🔴 **Однострочник — ДЕФОЛТ, план — исключение. Не наоборот.** *Цена 27.07: одна зона
(восемь файлов, один коммит) была отправлена через план — и застряла на четыре круга
терминала. Владелец: «не коммитится почему-то, может отложить на потом»; работа целого дня
чуть не осталась вне git.* Признак, по которому выбирается путь: **больше одного сообщения
коммита — план; одно — строка в чат.** Сомневаешься — строка.

⚠ **Формат `.commit-plan`: `==` — это ПРЕФИКС строки-сообщения, а не заглушка.**
Строка группы обязана начинаться с `== `, дальше текст сообщения. Шапка плана говорит
«Сообщения `==` переписать по-человечески», и это читается как «убрать `==` и написать
своё» — так и было прочитано. Итог: `❌ План начинается с пути, а не с "== сообщение"`.
*Цена 27.07: два лишних круга терминала поверх предыдущих двух.* Правильно:

```
== лекция Паскаля: тексты слайдов и разбор после эфира     ← == остаётся, меняется текст
lsh-2026-.../raskadrovka/RAZBOR-posle-lekcii-2026-07-27.md
```

Путь через план остаётся для ПАКЕТА разных коммитов:

1. `git_zona.py plan` собирает черновик `_studio/.commit-plan` из живого дерева. **Почему командой, а не руками:** дерево движется под руками (21.07 план по снимку 20-минутной давности устарел на 78 путей — рядом сделали `reset`). Сгенерированный план врать не успевает.
2. Переписать сообщения `==` по-человечески: что и зачем. Проверить, не попало ли то, чему в git не место (мусор, порождаемое → `.gitignore`; чужие зоны → не подметать).
3. Отдать владельцу ОДНУ команду — **всегда с `--push`**: `python3 _generator/tools/git_zona.py commit --push`.

🔴 **`--push` не опция, а часть команды.** Без него работа доезжает до `.git` и останавливается там: коммит есть, единственная копия — диск владельца. *Цена 23.07: Cowork выполнил этот шаг буквально, выдал `commit` без `--push` — и три коммита (приёмка разбора, +16 узлов картотеки, 18 ссылок маткостяка) остались только на машине владельца; поймал не гейт, а строка `doctor` про «есть только на этой машине», прочитанная случайно.* Расхождение было внутри одного дома: §1 предписывал владельцу `commit --push`, §2 велел Cowork выдавать `commit` — то есть буквальное исполнение канона давало дефект.

🔴 **Коммит НЕ ходит через руки владельца** (решение владельца 21.07, отменяет прежний «Cowork выдаёт блок `&&`, владелец вставляет»). *Почему: блок уезжал хенд-оффом — самым дырявым каналом фабрики (0 из 8 по статистике §Приёмка); плюс владелец вставлял цепочку `&&`, обрыв которой посреди НЕВИДИМ — цена 17.07: коммита не было час при живой параллельной работе.* План файлом убирает как класс: ручную сборку, подстановки `$(...)`, пути с пробелами (`kurs leto 2026/**`), невидимый обрыв `&&`.

⚠ **ВСЕ git-вызовы — с `--no-optional-locks`, включая «просто посмотреть».** Не исключение, а безусловное правило: без него Cowork отбирает лок у владельца.

**Приёмка любого отчёта — гейт 0 ПЕРВЫМ ходом, до чтения:**
```
python3 _generator/tools/git_zona.py check --zone <зона захода>
```
Красный → отчёт не принимается, что бы в нём ни было. (Полный ритуал приёмки — `RUKOVODSTVO-zahodami.md §Приёмка`.)

## 3. ИСПОЛНИТЕЛЮ (Claude Code) — коммитишь САМ, последним ходом

Ты host-side и в `.git` ПИШЕШЬ — значит коммитишь свою зону сам, никому не передавая. **Форма — ОБА хода, ни один не лишний:**

```
git --no-optional-locks add -- <пути зоны>                    # вводит НОВЫЕ пути в индекс
git --no-optional-locks commit -m "<зона>: <что>" -- <пути>   # отсекает всё чужое из индекса
python3 _generator/tools/git_zona.py check --zone <зона>      # из корня репо; должен быть ✅
git --no-optional-locks show --stat                           # обязаны быть ТОЛЬКО твои пути
```

- **`add` нужен**, потому что pathspec в `commit` знает ТОЛЬКО отслеживаемые пути: новый файл без `add` даёт `did not match any file(s) known to git`.
- **`-- <пути>` в самом `commit` нужен**, потому что `git commit -m` без путей забирает индекс ЦЕЛИКОМ — вместе с чужим, застейдженным кем угодно рядом.

*Обе половины оплачены 21.07 в один вечер: голый `commit` подмёл чужой индекс — коммит на 89 файлов вместо трёх, план из 10 коммитов схлопнулся в один свальный; потом «починка», убравшая `add`, завалила все 10 повторно (новых путей было три четверти). 125 путей остались вне git.* Держится не словом, а фикстурой (см. §5).

**Хук `pre-commit` («УРОК БЕЗ ЦЕНЫ») судит staged-пути.** Коммитишь свою зону — там только твоё, `--no-verify` НЕ нужен. Хук покраснел на ТВОИХ путях — значит в коммит уехало чужое: **не обходи, пересобери коммит.**

🔴 **Красное на ТВОЁМ новом `.md` («документ-сирота: нет строки в `KARTA.md §6`») чинится ОДНОЙ КОМАНДОЙ, а не обходом:**

```bash
python3 _generator/tools/register_doc.py <путь к .md внутри _studio/> "<описание одной фразой>"
```

Это единственная дверь к `_studio/docs/KARTA.md §6`; руками этот файл не правят. Идемпотентна, отказывает вне `_studio/`, на несуществующем файле и на пустом описании, печатает вписанную строку дословно. Свой файл-заход проводить через неё не надо — он рождается зарегистрированным из `bootstrap_zahod.py`. Дверь **не** подкоманда `git_zona.py` намеренно: тот объявлен единственной дверью к GIT, а регистрация к git отношения не имеет и обязана работать даже там, где `git_zona.py` из песочницы отказывает (`rc=3`).

🔴 **Позвал дверь — коммить `_studio/docs/KARTA.md` ТЕМ ЖЕ коммитом**, дописав его к своим путям и в `add`, и в `commit`. ⚠ Названный долг (дата данных 2026-07-30): ворота 5 читают `§6` **с диска, а не из индекса**, поэтому коммит без этого файла проходит ЗЕЛЁНЫМ — документ уезжает сиротой, а строка регистрации умирает при первом `checkout`. Пока это так, «исполнимость» достигнута только до момента коммита. Правильная починка — ворота 5 в режиме `--staged` читают `§6` из индекса (`git show :<путь>`) с откатом на HEAD; её риск назван честно и потому она отложена отдельным заходом: индекс-строгие ворота потребуют со-стейджить `KARTA.md` на КАЖДОМ коммите нового `.md`, а в репо трое писателей, и у соседа в этом файле могут лежать свои несохранённые правки.

*Цена, ради которой дверь заведена 2026-07-30 (заход `kod_registracia-bez-obhoda.md`).* Ворота 5 требовали регистрации, контракт зоны отдавал исполнителю `docs/` только на чтение — **два обязательных указания, невыполнимых разом**, и единственным выходом был обход. Автолог `../../zhurnal/_INFRA-git/INCIDENTY.md`: 28 обходов `--no-verify` из 56 срывов коммита, **27 из них по этой одной причине** — 48 % всей боли с коммитами, тринадцать исполнителей подряд. Механизм обхода при этом работал безупречно (причину требовал, писал сам, дедуплицировал) — чинить надо было не git, а правило. Держится не словом: `fixtures/register_doc/PROGNAT.sh`, пять ловушек, каждая проверена мутацией; охват объявлен строкой `# TOOL-CONTRACT-COVERS:` и поднимается хуком на правку любого из трёх файлов механизма.

⚠ **Но не всё в хуке судит staged-пути.** Фикстуры и общие гейты краснеют на ЧУЖОМ долге, и тогда чистая своя зона не коммитится вовсе — работа встаёт целиком (урок 9 арки `2026-07-25_lekcia-1`). Голого `git commit --no-verify` в этом репо нет: весь git идёт через инструмент, и до 27.07 у него флага не было — то есть обойти чужое красное было НЕЧЕМ. Теперь есть:

```bash
python3 _generator/tools/git_zona.py commit --zone <зона> \
        --no-verify "чужой долг: 51 мёртвая секция рамы" -m "<что и зачем>" --push
```

🔴 **ПРИЧИНА за флагом обязательна** — голый `--no-verify` отказывает. Обход, у которого не названо, ЧТО обходят, ничем не отличается от тихого: через неделю по записи не восстановить, чей это долг и закрыт ли он.

**Флаг законен только когда красное — чужое.** Своё красное чинится, а не обходится. Держится не словом: обход САМ пишет причину строкой в `INCIDENTY.md`. Все три половины (голый флаг отказывает · с причиной провозит · причина попала в лог) мутационно проверены ловушкой 15 фикстуры. Тот же долг назвать в отчёте захода (`ISTOCHNIK-PRAVDY §4.5`).

**Коммит не прошёл по ВНЕШНЕЙ причине** (чужой лок, конфликт, detached HEAD) — чужое состояние репозитория НЕ чини: зафиксируй файлы и напиши в отчёт отдельной строкой «коммита нет, причина такая-то, нужно ваше действие». Это законный отчёт. Молчаливое «сделано» при незакоммиченной зоне — брак: приёмка завернёт гейтом 0.

**В отчёт — строка `КОММИТ:`** с хэшем. Нет хэша — назови причину; пустая строка = отчёт не принимается.

## 4. ПАРАЛЛЕЛЬНЫЕ ЗАХОДЫ — свой worktree, а не своя ветка

🔴 **Регулярно идут два захода разом → каждому СВОЯ рабочая папка (worktree), а не «своя ветка».**

**Почему «разные ветки» было ХУЖЕ болезни.** У репозитория ОДНА рабочая папка на все ветки (`git worktree list` — один вход). Пока заход A работает, `git checkout` захода B **подменяет файлы под ногами A** — правки либо блокируют переключение, либо уезжают в чужую ветку. Прежний канон это предписывал («параллельным — разные ветки») и держался только тем, что заходы фактически шли по одному. При регулярной параллельной работе — это расписание аварий.

**Что даёт worktree:** свой индекс (чужое в твой коммит не попадёт ФИЗИЧЕСКИ), свой HEAD, своя папка. Хранилище объектов общее — 457 МБ стоит только рабочая копия, `.git` не дублируется.
**Чего НЕ даёт:** ссылки и упаковка объектов остаются общими ⇒ короткие блокировки при одновременном коммите сохраняются — их держит ретрай с отступом в `git_zona.py`. Два механизма дополняют друг друга.

**Как завести (Cowork):**
```
python3 _generator/tools/bootstrap_zahod.py <арка> <тема> --branch <ветка> --zone "<пути>" --worktree <имя>
```
`--worktree` заводит папку через `git_zona.py worktree add`, вписывает в заход `cd` ВМЕСТО `git checkout` и печатает ровно один вариант первого хода (развилку решает генератор — исполнитель с пустым контекстом гадать не должен). Забыл флаг, когда рядом живут другие папки или основная стоит на чужой ветке, — `bootstrap_zahod.py` предупредит.

🔴 **ОТМЕНЕНО 2026-08-03 — ПОРЯДОК БЫЛ ОПИСАН НЕВЕРНО, И КОД НИКОГДА ЕМУ НЕ СЛЕДОВАЛ.** `bootstrap_zahod.py` заводит worktree и пишет файл-заход ОДНИМ вызовом, так что «завести папку после того, как заход дописан» невыполнимо по построению. Установлено прогоном заходом `kod_dobivka-vetok.md`. **Действующее правило:** файл-заход живёт в ОДНОМ экземпляре, в основной папке, по абсолютному пути из стартовой строки; рабочая папка заводится только под КОД и файла-захода не содержит вовсе. Сверять копию с HEAD больше не требуется — копии нет.

🔴 **Новая подкоманда: `poteri`.**

| команда | что делает | кому |
|---|---|---|
| `poteri [--branch <в>]` | что пропадёт при удалении ветки: файлы, а не число коммитов; read-only, `rc=1` при реальной потере | всем |

*Прежняя редакция правила (отменена, оставлена как след): Worktree заводится ПОСЛЕ того, как заход дописан; копия сверяется с HEAD ДО старта работы. Папка копирует заход в момент создания — дописал раздел позже, и исполнитель работает по старой редакции, не зная об этом: разойтись здесь может ЛЮБОЙ раздел, включая критерий. Первым ходом захода в worktree — `diff` копии против HEAD; расхождение называется громко, до работы. *Цена: worktree заведён до того, как в заход добавили карту домов и раздел долгов рамы, — исполнитель недосчитался двух разделов выхода из трёх и пункта критерия. Спасло только то, что владелец продублировал заход текстом в чат: случайность канала, а не дисциплина.*

**Команды worktree:**
```
python3 _generator/tools/git_zona.py worktree add <имя> [--branch <ветка>]   # завести
python3 _generator/tools/git_zona.py worktree list                            # какие есть
python3 _generator/tools/git_zona.py worktree drop <имя>                      # снять (откажет при незакоммиченном)
```
`drop` с незакоммиченной работой НЕ удаляет ничего: автоочистка worktree — известный способ потерять заход безвозвратно (тот же дефект у claude-code — issue #55724).

**Тень после worktree-захода → `adopt`.** Заход отработал в worktree и закоммитил зону на СВОЕЙ ветке, а в основной папке осталась УСТАРЕВШАЯ untracked-копия той же зоны (тень). Руками это лечилось многоходовкой (`checkout <ветка> -- <зона>` + разбирательство с индексом); теперь — одна команда:
```
python3 _generator/tools/git_zona.py adopt --branch <ветка> --zone <зона>          # предпросмотр (ничего не меняет)
python3 _generator/tools/git_zona.py adopt --branch <ветка> --zone <зона> --yes    # заменить тень версией ветки и поставить в индекс
```
Без `--yes` — только показ диффа. После `--yes` — `commit --zone <зона>`. Ничего не теряется: хорошая версия на ветке цела, тень и так вне git. *Родился из урока 2026-07-23: worktree-заход оставил двойную копию зоны (`RUKOVODSTVO §Заход`).*

⚠ **Два исполнителя в ОДНОЙ рабочей папке одновременно — НЕТ, даже с непересекающимися зонами.** Либо развести по worktree, либо дождаться коммита первого.

🔴 **И «непересекающиеся зоны» внутри ОДНОЙ АРКИ невозможны в принципе — папка арки есть пересечение ВСЕГДА.** Файл-заход каждого исполнителя лежит в `../../zhurnal/<арка>/`, а закрывающая сессия получает всю папку арки целиком (иначе ей нечем править `UROKI-FABRIKE.md` и дневник). ⇒ **для ЗАКРЫВАЮЩЕГО захода и для любого второго захода в той же арке `--worktree` не опция, а требование**; `bootstrap_zahod.py` обязан отказываться собирать второй заход в основную папку, пока в арке есть незакоммиченные `kod_*.md` (долг инструмента, §5).
*Цена — шесть случаев на арке `2026-07-28_konspekt-l1`, один с реальным ущербом: заход обошёл покрасневший хук и был вынужден перейти с pathspec на `--zone teorkat-vvedenie`, префикс которого шире объявленной зоны, — и **закоммитил чужой файл (+20 строк) под своим сообщением**; он же сам это назвал «ровно тем механизмом, от которого предупреждает §3, только зашедшим не через голый `commit`, а через слишком широкий `--zone`». Другой заход едва не забрал незакоммиченную ленту владельца, исполнив шаблонную строку коммита буквально. Третий вынужденно расстажил файл, грязный ДО его старта и правившийся в параллельной сессии. Два получили красный гейт зоны на чужих путях и правильно его не чинили. Закрывающая сессия 30.07 не смогла сделать точку отката коммитом — рядом писался `kod_revizia.md` внутри её зоны — и сделала zip.*
⚠ **Гейт зоны не умеет зон из ОТДЕЛЬНЫХ ФАЙЛОВ: он судит каталог целиком и краснеет на чужом при чистом своём.** Это объявленная слепая зона, а не поломка: приёмке её предсказывать, исполнителю — не чинить чужое состояние.

🔴 **§4 захода подставляет пути из `--zone`, а не ПРИМЕР.** *Цена: в заходе, где зона была узкой, §4 давал готовую строку `commit -- teorkat-vvedenie/raskadrovka`, а контракт зоны двадцатью строками выше писал «ленту `raskadrovka/` НЕ ТРОГАЙ ВОВСЕ»; к моменту коммита лента была правлена параллельно. «Исполнив шаблонную строку §4 буквально, я забрал бы незакоммиченную ленту владельца под своё сообщение — **тот самый инцидент 21.07 (89 файлов вместо трёх), от которого §4 и защищает, только теперь его причиной был бы сам §4**.» Пример в шаблоне противоречит контракту зоны ровно в тех заходах, где зона узкая, то есть в самых аккуратных.*

## 4б. СЛИЯНИЕ ВЕТОК — `merge`, и почему конфликт разрешает НЕ инструмент

Заход в worktree кончается коммитом на своей ветке. Пока ветку не влили, **работа существует в двух версиях**, и они расходятся молча. Цена измерена 26.07: `arka/konsolidacia-l1` не была влита, потому что команды слияния в инструменте не существовало, а голый `git merge` в чат владельцу запрещён §0. За это время обе ветки писали одну картотеку врозь — разошлись на 25 карточек, из них **пять пар описывали одно и то же разными словами**.

```
python3 _generator/tools/git_zona.py merge <ветка>                          # влить в ТЕКУЩУЮ ветку
python3 _generator/tools/git_zona.py merge <ветка> --zone <путь> --zone <путь2>   # отказать, если тащит пути вне зон
python3 _generator/tools/git_zona.py merge --continue                       # завершить после разрешения конфликтов
python3 _generator/tools/git_zona.py merge --abort                          # откатить слияние целиком
```

До слияния команда печатает **что именно вливается**: базу, список коммитов, список затрагиваемых путей. `--zone` повторяем — заход законно держит несколько каталогов записи, одним префиксом они не накрываются; вне зон слияние не делается ВООБЩЕ.

**Чистота дерева проверяется точно, а не грубо.** Блокер — только грязный путь, который слияние собирается переписать; про остальную грязь команда предупреждает списком и сливает. Грубое «дерево должно быть чистым» в этом репо недостижимо (рядом всегда пишет третий) — а недостижимое условие вернуло бы всех к голому `git merge`, от которого мы уходим.

🔴 **Конфликт инструмент НЕ разрешает.** Он печатает конфликтные пути и останавливается: выбор между двумя версиями текста — смысловое решение, и «умное» авто-разрешение здесь означает потерю, которую никто не заметит (выпавшая карточка не отличается от невведённой). Разрешает человек или исполнитель захода, дальше `merge --continue`.

⚠ **Во время слияния `commit -- <пути>` невозможен** — git отказывает («cannot do a partial commit during a merge»). Поэтому merge-коммит собирается целиком из индекса: всё, что должно в него попасть, ставится явным `add` ДО завершения, а чужое незакоммиченное просто не ставится и остаётся в рабочем дереве.

## 4а. ЧТО ЖИВЁТ ВНЕ GIT (и почему) — `.gitignore`

Правило одно: **файл, который «делается» командой или скачиванием, в git не держим — держим ИСТОЧНИК.** Что попадает под него (решения владельца 2026-07-21):

- **`*/snapshots/`** — tar-архивы дерева. git сам и есть механизм снимков; архив дерева внутри git — снимок снимка.
- **`istochniki/ · biblioteka/ · literatura/` → `*.pdf`** — книги-источники (145 файлов, 333 МБ). Изданная книга «делается» скачиванием; она нужна НА ДИСКЕ для поиска, но не в репозитории. Рабочие pdf проекта (печатные листки, лендинги) под правило НЕ попадают — они не в библиотеках.
- **`carshering/`** — закрытая учебная работа, в архив; внутри был осиротевший gitlink.

⚠ **Бэкап-оговорка.** Пока файл в git, `git push` держит его копию на GitHub. Вне git единственная копия — на диске. Скачанное вернётся скачиванием; **невосстановимое** (сканы «Квант» 1970, конспекты курсов) держится ТОЛЬКО диском — это покрыто, лишь когда настроен Time Machine/облако. До того диск — единственная копия.

**Уже отслеживаемое `.gitignore` НЕ убирает** — снять с индекса отдельно (файлы на диске целы):
```
python3 _generator/tools/git_zona.py untrack          # показать, что снимется
python3 _generator/tools/git_zona.py untrack --yes    # снять
```
*Раньше здесь стоял shell-рецепт с `git rm --cached` и `xargs` — он ломался о zsh, пути с пробелами и разницу BSD/GNU (§0). Теперь это подкоманда: одинаково у всех, покрыта фикстурой «снимает с индекса, но НЕ удаляет с диска».*
**Вес `.git` это НЕ возвращает** — история остаётся. Вернуть место может только `git-filter-repo` (переписывает историю, `push --force`) — отдельная операция, с бэкапом `.git` и ТОЛЬКО когда есть бэкап диска.

## 5. ИНСТРУМЕНТ И ЕГО ЗАЩИТА ОТ РЕГРЕССИИ

**`_generator/tools/git_zona.py`** — вся работа с git, других дверей нет:

| Команда | Что делает | Кому |
|---|---|---|
| `doctor` | состояние: ветка, локи с возрастом, мусор, расхождение с origin, что вне git, **+ сторож соседних веток** (ниже) | всем, первым ходом |
| `check [--zone]` | краснеет (exit 1), если в зоне есть что-то вне git | приёмка, гейт 0 |
| `plan [--zone] [--force]` | черновик коммитов из ЖИВОГО дерева; не затирает уже вписанные сообщения | Cowork |
| `commit --zone <з> -m "<что>" [--push]` | ОДНОКОМАНДНАЯ ТРОПА: собрать пути зоны из живого дерева и закоммитить с этим сообщением, без плана; инварианты те же (общее ядро с план-путём) | владелец (Cowork готовит строку) |

Мусорный argv (например, хвост-«комментарий» `# …`, который zsh отдал программе) — отказ человеческим языком с диагнозом, не питоновый usage.

### 🔴 СТОРОЖ СОСЕДНИХ ВЕТОК в `doctor` (реализован 2026-07-30, дата данных та же)

Отвечает на единственный вопрос, который спас бы два дня 28.07: **нет ли моей зоны на другой ветке в более свежем виде.** Раньше `doctor` честно смотрел одну ветку и молчал, что их девять; работа, успешно закоммиченная не туда, где её будут искать, не отслеживалась ничем — `INCIDENTY.md` ведётся только по НЕудачным коммитам, а здесь все коммиты прошли.

Срабатывает **сам**, внутри `doctor`, отдельной команды нет: вспоминают только то, что уже болело. Печатает по каждой отставшей ветке — сколько коммитов не влито, дату последнего, **зоны** (`_studio/zhurnal/<арка>/` — в терминах `adopt --zone`) и **готовую команду лечения** (`adopt --branch … --zone …`, а на нескольких зонах — `merge <ветка>`).

Три свойства, каждое держится ловушкой и проверено мутацией:
- **ОХВАТ объявляется всегда, и на зелёном тоже** — «проверено N из N». Зелёное без охвата читается как «всё в порядке», а означает «в порядке то, что я смотрел». Не удалось прочитать ветку — охват падает и непрочитанная называется по имени.
- **Не шумит на здоровом** (`RESHENIYA Р31`): влитая целиком ветка (`HEAD..<ветка>` = 0) находкой не считается, сколько бы она ни отставала. Гейт, шумящий на здоровом, отключают — и пропадает вся защита.
- **READ-ONLY, `.git/index.lock` не берёт** — только `for-each-ref`/`rev-list`/`log`/`diff` через `--no-optional-locks`. Сторож, отбирающий лок у живого коммита, повторил бы дефект гейта, который лечит.

⚠ **Ветки считаются по ПОЛНОМУ `refs/heads/<имя>`, а не по короткому.** `%(refname:short)` укорачивает имя лишь до однозначности: при теге-омониме отдаёт `heads/vetka-a`, из чего собирался несуществующий `refs/heads/heads/vetka-a` — ветка уходила в «не прочитано», и сторож печатал **зелёное «невлитого нет» при живой невлитой работе**. Найдено мутацией при постановке ловушки; охват при этом честно падал до «1 из 2», но верят именно зелёному вердикту. Ветка вычекаученная в другой рабочей папке называется с пометкой — там может идти живой заход, и `merge` притащил бы недоделанное.

⚠ **Сторож называет, но НЕ удаляет и не вливает сам.** Влитая ветка удаляется только решением владельца; вливание — смысловое решение, как и разрешение конфликта (§4б).

- Фикстура ПЕРВЫМ ходом вычищает окружение: `unset $(git rev-parse --local-env-vars)` — каноничная форма из документации githooks. *Без неё гейт, запущенный хуком, коммитил в БОЕВОЙ репозиторий: git внутри хука экспортирует `GIT_DIR`/`GIT_INDEX_FILE` абсолютными путями. Цена 21.07: фикстура создала мусорный коммит `baseline` автором `fixture` и перезаписала git-личность владельца.*
- Хук `pre-commit` поднимает её при правке `git_zona.py` (через `env -u` — второй слой) и только тогда: «шумит только по делу».
- Работает на одноразовом репо в `/tmp` через `GIT_ZONA_REPO` — в боевом проверять поведение git нельзя.

⚠ **Гейт — тоже код, и он опаснее проверяемого.** Проверять его надо в ТЕХ условиях, где он сработает (внутри хука, с наследованным окружением), а не в удобных. «Фикстура зелёная» без указания условий запуска — недоказанный вердикт, как «дыр не найдено» без охвата.

⚠ **Починка СООБЩЕНИЯ проверяется на ВСЕХ ветках, где это сообщение печатается, — иначе чинится симптом, а не класс.** Закон «инструмент не смеет печатать тревогу на здоровом исходе» действует и на порядок строк: успешный исход, напечатанный ВТОРЫМ, читается как провал. Ловушка обязана быть на КАЖДУЮ ветку исполнения, а не на ту, где дефект нашли. *Цена: ловушка 8 закрыла «плана нет» для ЧИСТОГО дерева; при грязном сообщение по-прежнему начиналось со строки «Плана нет, но в дереве N путей вне git», а хэш последнего коммита стоял второй строкой. 28.07 владелец прислал скриншот с подписью «коммит не прошёл почему-то» — коммит прошёл, `f9199ff`, вместе с push, за минуту до этого. Два раза за неделю владелец потратил ход на выяснение, прошёл ли коммит; оба раза он проходил, второй — при живом уроке в дневнике арки. Починено перестановкой строк: первой идёт `✅ Последний коммит на месте: <хэш>`.*

### 🔴 НАЗВАННЫЕ ДОЛГИ `git_zona.py` (дата данных: 2026-07-30, арка `2026-07-28_konspekt-l1`)

Долги названы здесь, а не только в борде, потому что исполнитель читает этот файл, а борд — нет; каждый упирался в них ночью, поодиночке, и трое из четырёх обошли канон.

1. **`add` внутри инструмента падает на УДАЛЁННЫХ путях.** Он перечисляет пути поштучно, и на пути, застейдженном как удалённый, даёт `fatal: pathspec … did not match any files`, `rc=128` — коммит не делается ВООБЩЕ. Хуже диагностика: инструмент печатает не причину, а «Причину покажет `doctor`», а `doctor` про упавший `add` не говорит ничего. **Четыре независимых отказа за одну арку** (`kod_final`, `kod_chistka`, `kod_podgonka`, `kod_dobivka`).
2. **Зона из НЕСКОЛЬКИХ КОРНЕЙ инструменту не выражается** (`--zone` берёт один префикс). Обходят двумя коммитами, и первый оказывается шире объявленной зоны — см. ущерб в §4.
3. **Следствие 1+2 — самое дорогое: причина обхода НЕ доезжает в `INCIDENTY.md`.** Механизм «обход сам пишет причину в лог» работает только ЧЕРЕЗ инструмент; когда инструмент падает, единственным путём остаётся голый `git commit --no-verify`, и запись о долге не появляется. За арку так ушли два коммита, и один исполнитель прямо написал: «это долг: строку в `INCIDENTY.md` надо внести аналитику, текст причины — в теле коммита». *И `kod_final` зафиксировал обратный порядок: запись об обходе уехала в `INCIDENTY.md` РАНЬШЕ падения — «причина там есть, а коммита к ней нет, сверьте».*
4. **Устаревший черновик `.commit-plan` блокирует коммит и выглядит как поломка git.** *Цена названа владельцем: «почему-то уже второй раз не проходит коммит» — **владелец потерял два захода на попытки**. Инструмент печатал «в плане остались неотредактированные сообщения — их 3», а причина была в плейсхолдерах от более раннего хода; дерево и права ни при чём.* Лечение однострочное: либо `plan` перезаписывается сам при устаревании, либо `commit` называет в ошибке ВОЗРАСТ черновика и предлагает `--force`.
5. **`bootstrap_zahod.py` не отказывается собирать второй заход в основную папку** при незакоммиченных `kod_*.md` в той же арке (§4).

⚠ **И общее, не про git:** `rc=0` конвейера — НЕ код возврата первой команды. За арку один исполнитель прочитал код `tail` как успех коммита (HEAD не двинулся, хук блокировал), другой — что `${PIPESTATUS[0]}` в zsh не работает вовсе, там `$pipestatus[1]`. Это уточнение к правилу «код возврата первым», у которого своя цена оплачена 21.07.

## 7. 🔴 РАЗВЕНЧАННЫЙ ФАНТОМ: «в репозитории живёт авто-коммит»

Несколько разборов 21.07 (и ряд уроков арки `mat-kostyak`) называли причиной загрязнения индекса **авто-коммит**, якобы стейджащий всё дерево между командами. **Его НЕТ и не было** (проверено по живым файлам): единственный хук — `.githooks/pre-commit`, он гоняет `check_uroki.py` и НЕ стейджит ничего; `_studio/.commit-plan` не упоминается нигде, кроме `git_zona.py`; ни cron, ни launchd. Проверить: `git --no-optional-locks config --get core.hooksPath && cat .githooks/*`.

**Что грязнит индекс на самом деле:** живые писатели — владелец, Cowork, Claude Code — через ОБЩИЙ индекс общей рабочей папки. Наблюдения (89 файлов, 108 путей в чужом индексе) были реальны; неверна была только приписанная им причина. Отсюда два верных следствия, оба уже в силе: pathspec-форма коммита (§3) защищает от грязного индекса независимо от того, кто его грязнит; worktree (§4) убирает сам общий индекс при параллельной работе.

*Почему это важно как урок: из фантома вывели ложный закон «НИКОГДА `add` → `commit`», который прямо воспроизводил поломку (без `add` новые файлы не коммитятся) — при том что рабочий инструмент делает именно `add` → `commit`. Правило, которому противоречит его единственная реализация, — не правило, а описка, и она дороже отсутствия правила.*
