## 0. 🔴 ЗАКОН, ИЗ КОТОРОГО СЛЕДУЕТ ВСЁ ОСТАЛЬНОЕ

**COWORK НЕ ВЫДАЁТ ВЛАДЕЛЬЦУ SHELL. Только вызовы `python3 _generator/tools/git_zona.py <команда>`.**

Запрещено выдавать в чат: `rm`, `find`, `xargs`, `git rm --cached`, glob-шаблоны (`*.lock`), подстановки `$(...)`, цепочки `&&`, многострочные конструкции — что угодно, что владелец копирует и исполняет своим шеллом.

*Почему это закон, а не стилистика.* Cowork пишет команды в **bash под Linux** (песочница), а исполняются они в **zsh под macOS**. Разница сред ломает их систематически, и каждый раз выглядит как «git опять не работает»:

| Что сломалось | Как | Когда |
|---|---|---|
| `rm -f .git/*.lock` | в zsh несовпавший glob роняет **всю строку** (`no matches found`); уборка не выполнилась, а владелец думал, что выполнилась | 22.07 |
| `cd /sessions/...` | путь песочницы, на машине владельца такого нет → `fatal: not a git repository` | 11.07, снова 22.07 |
| цепочка `... && ... && ...` | обрыв в середине НЕВИДИМ: `&&` молча не идёт дальше, владелец добросовестно говорит «сделал» | 17.07, коммита не было час |
| `xargs -0` / `-r` | BSD и GNU ведут себя по-разному | 21.07 |
| `$(git ls-files …)` | в репо есть пути с пробелами (`kurs leto 2026/**`) — аргумент расщепляется | 17.07 |

🔴 **То же правило — для КОДА, который исполняется у владельца: фикстуры и хуки.** Они гоняются на macOS (BSD-утилиты), а пишутся в Linux-песочнице (GNU). Никаких `touch -d`, `date -d`, `sed -i`, `xargs -r`, `stat -c`, `grep -P` — нужен нетривиальный системный вызов, делай его `python3 -c`, он одинаков везде. *Цена (23.07): в фикстуре `clean` стояло `touch -d '10 minutes ago'`; на macOS BSD-touch этого не понимает, fallback создал файл с текущим временем, лок посчитался свежим — **фикстура остановила здоровый коммит владельца**, оставаясь зелёной у Cowork. Гейт, зелёный у автора и красный у владельца, хуже отсутствующего гейта.* Проверка на портируемость — грепом:
```
grep -nE "touch -d|date -d|sed -i|xargs -r|stat -c|grep -P" _generator/tools/fixtures/*/PROGNAT.sh .githooks/*
```

⇒ **Нужна операция, которой нет в списке команд ниже — не выдавай shell, а добавь подкоманду в `git_zona.py`.** Она кроссплатформенна, покрыта фикстурой и ведёт себя одинаково у всех. Так появились `clean` и `untrack`: обе родились из shell-команд, которые не сработали у владельца.

## 1. ВЛАДЕЛЬЦУ — шесть команд, больше знать нечего

Ты команды не собираешь и в git руками не ходишь. Всегда одно и то же начало:

```
cd /Users/ivanyakovlev/Documents/GitHub/materials

python3 _generator/tools/git_zona.py doctor          # что с репо прямо сейчас
python3 _generator/tools/git_zona.py plan            # собрать черновик коммитов
python3 _generator/tools/git_zona.py commit --push   # закоммитить по плану и вывезти
python3 _generator/tools/git_zona.py check           # что осталось вне git
python3 _generator/tools/git_zona.py clean           # снять мёртвые локи и мусор
python3 _generator/tools/git_zona.py untrack --yes   # убрать из git то, что попало в .gitignore
```

**Не помнишь, какая нужна — запускай `doctor`.** Он называет состояние и следующий шаг.
`commit` сам снимает мёртвый лок перед работой, сам ждёт чужой живой коммит и сам сверяет по живым файлам, что всё доехало.

**Когда «Claude просит закоммитить»:** `doctor` → если вне git есть лишнее, `plan` → Claude (или ты) правит сообщения `==` в `_studio/.commit-plan` → `commit`. Скрипт сам дождётся чужого коммита, сам сверит по живым файлам, что всё доехало, и покраснеет, если нет.

**Сломалось непонятное — не разбирайся.** Запусти `doctor` и покажи вывод Claude целиком. Вывод самодостаточен (ветка, лок, недоделанные merge/rebase, расхождение с origin, всё вне git) — диагноз ставится без доступа к твоей машине.

**«Не коммитится» почти всегда одно из трёх** (`doctor` называет прямо):

- **лок занят** — рядом идёт чужой коммит. НЕ поломка: `commit` ждёт сам до 90 с. Лок руками не удалять НИКОГДА (снести у работающего git — испортить индекс; из песочницы проверка «жив ли git» слепа).
- **незаконченный merge/rebase** — пока висит, обычный коммит не пройдёт.
- **detached HEAD** — ты не на ветке, коммит потеряется при переключении.

**Мёртвый лок.** Больше не твоя забота: `commit` снимает его сам, а явно — `clean`. Свежий (младше 5 мин) не трогается никогда: там может идти живой чужой коммит, и снести его — испортить индекс. *Цена, ради которой это автоматизировано: замок держал репозиторий закоммитить-неспособным 28 часов (157 путей вне git), а выданная руками команда уборки не сработала дважды — падала на zsh (§0).*

## 2. COWORK (аналитику) — план файлом, не блок в чат

🔴 **COWORK В ПЕСОЧНИЦЕ — НЕ КОММИТЕР. Это закрытая развилка, а не осторожность** (решено 2026-07-22 экспериментом, после трёх отказов за сессию).

**Почему не «просто другая форма коммита».** В песочнице запрещён `unlink` во ВСЁМ монтировании (не только в `.git`). Git при любой записи создаёт временные файлы и потом их удаляет — удалить не может, они остаются минами и блокируют репозиторий для всех троих писателей. Проверено на одноразовом репозитории внутри того же монтирования:

| Что пробовали | Что осталось в `.git` | Годится? |
|---|---|---|
| `commit -- <pathspec>` (канон для host-side) | `next-index-<PID>.lock`, `index.lock`, `HEAD.lock`; следующий git падает `File exists` — PID в контейнере мелкие и переиспользуются | ❌ |
| ОБЫЧНЫЙ `commit` без pathspec | мин меньше, но `HEAD.lock` и `objects/**/tmp_obj_*` остаются ВСЁ РАВНО | ❌ — «другая форма» не лечит |
| `GIT_INDEX_FILE` в `/tmp` | git всё равно кладёт `next-index-*.lock` ВНУТРЬ `.git` | ❌ тупик |

⚠ **Коммит при этом технически СОЗДАЁТСЯ** — поэтому соблазн «ну ведь прошло же» силён, а цену платит следующий, кто упрётся в чужой лок. *Цена 22.07: репозиторий дважды вставал примерно на полчаса; снять лок из песочницы нечем — каждый раз нужен был владелец.*

**Держится механизмом, а не словом:** `git_zona.py` определяет песочницу (репозиторий смонтирован через FUSE) и `commit` / `worktree add|drop` **отказываются работать**, печатая готовую команду владельцу. Чтение (`check`, `plan`, `doctor`, `worktree list`) работает как обычно. *Раньше запрет жил только в тексте — и был нарушён: правило, которое можно нарушить молча, будет нарушено (`../KONSTITUCIYA.md §11`).*

⚠ **Выдавая команду владельцу, подставь путь ЕГО машины.** Путь песочницы (`/sessions/...`) у него не существует — будет `fatal: not a git repository` (инцидент 2026-07-11).

**Ты в `.git` НЕ пишешь** (песочница). Поэтому свою зону — документацию — коммитишь так:

1. `git_zona.py plan` собирает черновик `_studio/.commit-plan` из живого дерева. **Почему командой, а не руками:** дерево движется под руками (21.07 план по снимку 20-минутной давности устарел на 78 путей — рядом сделали `reset`). Сгенерированный план врать не успевает.
2. Переписать сообщения `==` по-человечески: что и зачем. Проверить, не попало ли то, чему в git не место (мусор, порождаемое → `.gitignore`; чужие зоны → не подметать).
3. Отдать владельцу ОДНУ команду — **всегда с `--push`**: `python3 _generator/tools/git_zona.py commit --push`.

🔴 **`--push` не опция, а часть команды.** Без него работа доезжает до `.git` и останавливается там: коммит есть, единственная копия — диск владельца. *Цена 23.07: Cowork выполнил этот шаг буквально, выдал `commit` без `--push` — и три коммита (приёмка разбора, +16 узлов картотеки, 18 ссылок маткостяка) остались только на машине владельца; поймал не гейт, а строка `doctor` про «есть только на этой машине», прочитанная случайно.* Расхождение было внутри одного дома: §1 предписывал владельцу `commit --push`, §2 велел Cowork выдавать `commit` — то есть буквальное исполнение канона давало дефект.

🔴 **Коммит НЕ ходит через руки владельца** (решение владельца 21.07, отменяет прежний «Cowork выдаёт блок `&&`, владелец вставляет»). *Почему: блок уезжал хенд-оффом — самым дырявым каналом фабрики (0 из 8 по статистике §Приёмка); плюс владелец вставлял цепочку `&&`, обрыв которой посреди НЕВИДИМ — цена 17.07: коммита не было час при живой параллельной работе.* План файлом убирает как класс: ручную сборку, подстановки `$(...)`, пути с пробелами (`kurs leto 2026/**`), невидимый обрыв `&&`.

⚠ **ВСЕ git-вызовы — с `--no-optional-locks`, включая «просто посмотреть».** Не исключение, а безусловное правило: без него Cowork отбирает лок у владельца.

**Приёмка любого отчёта — гейт 0 ПЕРВЫМ ходом, до чтения:**
```
python3 _generator/tools/git_zona.py check --zone <зона захода>
```
Красный → отчёт не принимается, что бы в нём ни было. (Полный ритуал приёмки — `RUKOVODSTVO-zahodami.md §Приёмка`.)

## 3. ИСПОЛНИТЕЛЮ (Claude Code) — коммитишь САМ, последним ходом

Ты host-side и в `.git` ПИШЕШЬ — значит коммитишь свою зону сам, никому не передавая. **Форма — ОБА хода, ни один не лишний:**

```
git --no-optional-locks add -- <пути зоны>                    # вводит НОВЫЕ пути в индекс
git --no-optional-locks commit -m "<зона>: <что>" -- <пути>   # отсекает всё чужое из индекса
python3 _generator/tools/git_zona.py check --zone <зона>      # из корня репо; должен быть ✅
git --no-optional-locks show --stat                           # обязаны быть ТОЛЬКО твои пути
```

- **`add` нужен**, потому что pathspec в `commit` знает ТОЛЬКО отслеживаемые пути: новый файл без `add` даёт `did not match any file(s) known to git`.
- **`-- <пути>` в самом `commit` нужен**, потому что `git commit -m` без путей забирает индекс ЦЕЛИКОМ — вместе с чужим, застейдженным кем угодно рядом.

*Обе половины оплачены 21.07 в один вечер: голый `commit` подмёл чужой индекс — коммит на 89 файлов вместо трёх, план из 10 коммитов схлопнулся в один свальный; потом «починка», убравшая `add`, завалила все 10 повторно (новых путей было три четверти). 125 путей остались вне git.* Держится не словом, а фикстурой (см. §5).

**Хук `pre-commit` («УРОК БЕЗ ЦЕНЫ») судит staged-пути.** Коммитишь свою зону — там только твоё, `--no-verify` НЕ нужен. Хук покраснел — значит в коммит уехало чужое: **не обходи, пересобери коммит.**

**Коммит не прошёл по ВНЕШНЕЙ причине** (чужой лок, конфликт, detached HEAD) — чужое состояние репозитория НЕ чини: зафиксируй файлы и напиши в отчёт отдельной строкой «коммита нет, причина такая-то, нужно ваше действие». Это законный отчёт. Молчаливое «сделано» при незакоммиченной зоне — брак: приёмка завернёт гейтом 0.

**В отчёт — строка `КОММИТ:`** с хэшем. Нет хэша — назови причину; пустая строка = отчёт не принимается.

## 4. ПАРАЛЛЕЛЬНЫЕ ЗАХОДЫ — свой worktree, а не своя ветка

🔴 **Регулярно идут два захода разом → каждому СВОЯ рабочая папка (worktree), а не «своя ветка».**

**Почему «разные ветки» было ХУЖЕ болезни.** У репозитория ОДНА рабочая папка на все ветки (`git worktree list` — один вход). Пока заход A работает, `git checkout` захода B **подменяет файлы под ногами A** — правки либо блокируют переключение, либо уезжают в чужую ветку. Прежний канон это предписывал («параллельным — разные ветки») и держался только тем, что заходы фактически шли по одному. При регулярной параллельной работе — это расписание аварий.

**Что даёт worktree:** свой индекс (чужое в твой коммит не попадёт ФИЗИЧЕСКИ), свой HEAD, своя папка. Хранилище объектов общее — 457 МБ стоит только рабочая копия, `.git` не дублируется.
**Чего НЕ даёт:** ссылки и упаковка объектов остаются общими ⇒ короткие блокировки при одновременном коммите сохраняются — их держит ретрай с отступом в `git_zona.py`. Два механизма дополняют друг друга.

**Как завести (Cowork):**
```
python3 _generator/tools/bootstrap_zahod.py <арка> <тема> --branch <ветка> --zone "<пути>" --worktree <имя>
```
`--worktree` заводит папку через `git_zona.py worktree add`, вписывает в заход `cd` ВМЕСТО `git checkout` и печатает ровно один вариант первого хода (развилку решает генератор — исполнитель с пустым контекстом гадать не должен). Забыл флаг, когда рядом живут другие папки или основная стоит на чужой ветке, — `bootstrap_zahod.py` предупредит.

**Команды worktree:**
```
python3 _generator/tools/git_zona.py worktree add <имя> [--branch <ветка>]   # завести
python3 _generator/tools/git_zona.py worktree list                            # какие есть
python3 _generator/tools/git_zona.py worktree drop <имя>                      # снять (откажет при незакоммиченном)
```
`drop` с незакоммиченной работой НЕ удаляет ничего: автоочистка worktree — известный способ потерять заход безвозвратно (тот же дефект у claude-code — issue #55724).

⚠ **Два исполнителя в ОДНОЙ рабочей папке одновременно — НЕТ, даже с непересекающимися зонами.** Либо развести по worktree, либо дождаться коммита первого.

## 4а. ЧТО ЖИВЁТ ВНЕ GIT (и почему) — `.gitignore`

Правило одно: **файл, который «делается» командой или скачиванием, в git не держим — держим ИСТОЧНИК.** Что попадает под него (решения владельца 2026-07-21):

- **`*/snapshots/`** — tar-архивы дерева. git сам и есть механизм снимков; архив дерева внутри git — снимок снимка.
- **`istochniki/ · biblioteka/ · literatura/` → `*.pdf`** — книги-источники (145 файлов, 333 МБ). Изданная книга «делается» скачиванием; она нужна НА ДИСКЕ для поиска, но не в репозитории. Рабочие pdf проекта (печатные листки, лендинги) под правило НЕ попадают — они не в библиотеках.
- **`carshering/`** — закрытая учебная работа, в архив; внутри был осиротевший gitlink.

⚠ **Бэкап-оговорка.** Пока файл в git, `git push` держит его копию на GitHub. Вне git единственная копия — на диске. Скачанное вернётся скачиванием; **невосстановимое** (сканы «Квант» 1970, конспекты курсов) держится ТОЛЬКО диском — это покрыто, лишь когда настроен Time Machine/облако. До того диск — единственная копия.

**Уже отслеживаемое `.gitignore` НЕ убирает** — снять с индекса отдельно (файлы на диске целы):
```
python3 _generator/tools/git_zona.py untrack          # показать, что снимется
python3 _generator/tools/git_zona.py untrack --yes    # снять
```
*Раньше здесь стоял shell-рецепт с `git rm --cached` и `xargs` — он ломался о zsh, пути с пробелами и разницу BSD/GNU (§0). Теперь это подкоманда: одинаково у всех, покрыта фикстурой «снимает с индекса, но НЕ удаляет с диска».*
**Вес `.git` это НЕ возвращает** — история остаётся. Вернуть место может только `git-filter-repo` (переписывает историю, `push --force`) — отдельная операция, с бэкапом `.git` и ТОЛЬКО когда есть бэкап диска.

## 5. ИНСТРУМЕНТ И ЕГО ЗАЩИТА ОТ РЕГРЕССИИ

**`_generator/tools/git_zona.py`** — вся работа с git, других дверей нет:

| Команда | Что делает | Кому |
|---|---|---|
| `doctor` | состояние: ветка, локи с возрастом, мусор, расхождение с origin, что вне git | всем, первым ходом |
| `check [--zone]` | краснеет (exit 1), если в зоне есть что-то вне git | приёмка, гейт 0 |
| `plan [--zone] [--force]` | черновик коммитов из ЖИВОГО дерева; не затирает уже вписанные сообщения | Cowork |
| `commit [--zone] [--push]` | исполняет план; сам снимает мёртвый лок, ждёт чужой живой, сверяет результат по файлам | владелец |
| `clean` | снимает мёртвые локи (старше 5 мин) и мусорные `tmp_obj_*`; свежие не трогает | владелец |
| `untrack [--yes]` | снимает с индекса то, что попало под `.gitignore`; диск не трогает | владелец |
| `worktree add/list/drop` | рабочая папка на параллельный заход (§4) | Cowork готовит, владелец запускает |

Всё через `--no-optional-locks`. Пишущие команды (`commit`, `clean`, `untrack`, `worktree add/drop`) в песочнице **отказываются работать** (§2).

**`_generator/tools/fixtures/git_zona/PROGNAT.sh`** — фикстура инструмента. Семь ловушек, каждая с оплаченной ценой; все проверены МУТАЦИЕЙ (гейт, который не умеет падать, — театр):

1. убран `add` → новые файлы не доезжают;
2. убран pathspec → чужой застейдженный файл уезжает в коммит;
3. сломан детект песочницы — в обе стороны: «никогда не песочница» (запрет мёртв) и «всегда песочница» (ломает владельца и Claude Code);
4. `clean` снёс СВЕЖИЙ лок (можно испортить чужой индекс) или не снял мёртвый;
5. `untrack` удалил файл с диска вместо разотслеживания;
6. канон отстал от инструмента — подкоманда есть, а в `GIT-disciplina.md` её нет;
7. GNU-изм в фикстуре или хуке (`touch -d`, `date -d`, `sed -i`, `xargs -r`, `stat -c`, `grep -P`).

- Фикстура ПЕРВЫМ ходом вычищает окружение: `unset $(git rev-parse --local-env-vars)` — каноничная форма из документации githooks. *Без неё гейт, запущенный хуком, коммитил в БОЕВОЙ репозиторий: git внутри хука экспортирует `GIT_DIR`/`GIT_INDEX_FILE` абсолютными путями. Цена 21.07: фикстура создала мусорный коммит `baseline` автором `fixture` и перезаписала git-личность владельца.*
- Хук `pre-commit` поднимает её при правке `git_zona.py` (через `env -u` — второй слой) и только тогда: «шумит только по делу».
- Работает на одноразовом репо в `/tmp` через `GIT_ZONA_REPO` — в боевом проверять поведение git нельзя.

⚠ **Гейт — тоже код, и он опаснее проверяемого.** Проверять его надо в ТЕХ условиях, где он сработает (внутри хука, с наследованным окружением), а не в удобных. «Фикстура зелёная» без указания условий запуска — недоказанный вердикт, как «дыр не найдено» без охвата.

## 7. 🔴 РАЗВЕНЧАННЫЙ ФАНТОМ: «в репозитории живёт авто-коммит»

Несколько разборов 21.07 (и ряд уроков арки `mat-kostyak`) называли причиной загрязнения индекса **авто-коммит**, якобы стейджащий всё дерево между командами. **Его НЕТ и не было** (проверено по живым файлам): единственный хук — `.githooks/pre-commit`, он гоняет `check_uroki.py` и НЕ стейджит ничего; `_studio/.commit-plan` не упоминается нигде, кроме `git_zona.py`; ни cron, ни launchd. Проверить: `git --no-optional-locks config --get core.hooksPath && cat .githooks/*`.

**Что грязнит индекс на самом деле:** живые писатели — владелец, Cowork, Claude Code — через ОБЩИЙ индекс общей рабочей папки. Наблюдения (89 файлов, 108 путей в чужом индексе) были реальны; неверна была только приписанная им причина. Отсюда два верных следствия, оба уже в силе: pathspec-форма коммита (§3) защищает от грязного индекса независимо от того, кто его грязнит; worktree (§4) убирает сам общий индекс при параллельной работе.

*Почему это важно как урок: из фантома вывели ложный закон «НИКОГДА `add` → `commit`», который прямо воспроизводил поломку (без `add` новые файлы не коммитятся) — при том что рабочий инструмент делает именно `add` → `commit`. Правило, которому противоречит его единственная реализация, — не правило, а описка, и она дороже отсутствия правила.*
