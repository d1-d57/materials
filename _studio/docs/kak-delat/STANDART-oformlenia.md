## 1. Зачем оформление (единственная причина)

Этот HTML — **внутренний рабочий вид**, не публикация. Причина, по которой он вообще существует, одна:

> **В markdown невозможно читать длинный концептуально плотный мат-текст.** Формулы не набраны, структура не видна, второй слой негде держать. В HTML — можно.

Отсюда единственный критерий любого визуального решения:

> **Визуал работает на понимание и на укладывание СТРУКТУРЫ текста в голове. Всё, что не работает на это, — не делаем.**

Не «красиво», не «богато», не «фирменно». Украшение, не несущее структуры, — брак ровно как вода в тексте (`STANDART-teksta.md`, правило 5).

## 2. Главный инвариант: автор пишет markdown, который писал и так

**Автор не учит новый синтаксис.** Он пишет по `STANDART-teksta.md` — с номерами, именами и статусами, — а генератор **распознаёт тип блока и красит сам**.

> Пишешь `**Определение 12 (действие $e_i$).** Пусть $v$ — состояние…` → получаешь синюю врезку с якорем и пунктом в оглавлении. Ничего не размечая.

**Почему так, а не через явные теги.** Разметка, которую надо помнить, не переживает и одной сессии: автор пишет содержание, а не HTML. Единственный способ получить *всегда* одинаковый вид — вывести его из того, что автор пишет естественно. Это же и гейт: **если текст написан по контракту — он и выглядит правильно; если блок не покрасился, значит статус не проставлен** (правило 1), то есть вид работает индикатором брака.

### ⚠ Конвенция слитного блока (единственное, что автор обязан помнить)

Движок красит блок markdown; **граница блока — пустая строка**. Значит:

> **Типизированный блок пишется СЛИТНО — без пустых строк внутри.** Тогда в цветную рамку попадает всё утверждение целиком: метка, текст, `$$`-формулы, хвост.

Разобьёшь пустой строкой — в рамку попадёт только зачин, а хвост прольётся наружу обычным текстом (метка и цвет останутся, но рамка оборвётся). Проверено пробой 2026-07-16: слитный блок с двумя display-формулами и хвостом → всё внутри `.stmt.defn`; тот же блок с пустыми строками → в рамке одна метка.

```markdown
✅  **Определение 1 (алгебра).** Зафиксируем $\delta$. Алгебра задана соотношениями
    $$e_i^2=\delta e_i,$$
    $$e_ie_{i\pm1}e_i=e_i,$$
    где индексы пробегают допустимые значения.

❌  **Определение 1 (алгебра).** Зафиксируем $\delta$. Алгебра задана соотношениями
    ⏎
    $$e_i^2=\delta e_i,$$
    ⏎
    где индексы пробегают допустимые значения.     ← хвост вывалится из рамки
```

*Почему конвенцией, а не кодом.* Собрать хвосты в рамку автоматически = stateful-парсер, поглощающий блоки до терминатора, то есть переписывание модели данных движка (поток блоков) — риск, несопоставимый с пользой. Правило письма стоит одну строку и ничего не ломает.

**Правило цвета — не декоративное:** цвет кодирует **статус утверждения**. Синий = «это определение, всё честно определено». Тёплый = «это утверждение, у него есть формулировка». Приглушённый = «это доказательство». Пунктир = «за это мы не платили» (чёрный ящик). Пролистывая текст, автор видит **скелет доказательной структуры**, не читая слов. Это и есть цель §1.

## 4. Макет — три зоны

```
[ оглавление 210px ][ текст ≤820 ][ жёлоб полей ~195 ]
        sticky            main            .mn float
```

- **Оглавление** — `position:sticky`, авто-нумерация, подсветка активного пункта при скролле. Это **карта текста**: главный инструмент «уложить структуру в голове».
- **Текст** — `max-width:820px`. Шире не делать: длина строки важнее заполнения экрана.
- **Жёлоб полей** — `.mn` уходит вправо через отрицательный margin. Второй слой (оговорки, отсылки, «на самом деле») **не рвёт основную нить**.
- Общий грид: `.layout{display:grid;grid-template-columns:210px minmax(0,1015px);gap:46px;max-width:1275px}`.

## 5. Токены (каталанская база — решение владельца 2026-07-16)

```css
--text:#211f1b;  --muted:#726c60;
--accent:#2f6e8e;  --accent-soft:#e8f0f4;     /* определения, оглавление, ссылки */
--warm:#c9743a;    --warm-soft:#f6ece2;       /* утверждения, оговорки */
--bg:#fbfaf6;      --rule:#e7e2d6;  --shade:#dfeaf0;
```

**Типографика.** Текст — `"Source Serif 4", Georgia, serif`, **21px / 1.7**. Интерфейс, заголовки, метки, подписи SVG — `"Source Sans 3", system-ui, sans-serif`. Засечки для чтения, гротеск для навигации — разделение несёт смысл: гротеском набрано всё, что *не* текст.

**Заголовки.** `h2` — авто-нумерация через `counter(sec)`, номер акцентом. ⚠ **Номера руками не писать** — будет двойная нумерация (реальный баг 2026-07-16).

**Сюжетные цвета нитей** (`--s-*`, из научпоп-эталона) — опция для длинных текстов со сквозными линиями; в мат-тексте по умолчанию НЕ включаются.

## 6. Иллюстрации

> **⚠ ДОМ ПРАВИЛ РИСОВАНИЯ — `../../konvejer/09-illustracii/SLOVAR-primitivov.md`.** Там общий словарь примитивов (узел · ребро · дуга · путь · дефект · многоугольник · клетка · ось · построение · стрелка · метка), главное правило «внутри рисунка только МЕТКА, проза — в подпись», сетка, ловушки и дисциплина «нет примитива или вышло плохо → чинить словарь». Словарь ОБЩИЙ со слайдами (арка 9): рисуем одним языком на обоих носителях. **Читать ПЕРЕД рисованием.** Ниже — только то, что специфично для doc-вида.

**Формат — инлайн-SVG в `<figure>`, не растр.** Причина: рисунок правится текстом (в том числе Claude), масштабируется, весит килобайты, наследует палитру документа через классы.

Палитра рисунка (обязательна — рисовать классами, не атрибутами):

| Класс | Что |
|---|---|
| `.s-line` | основная линия (2px, `--text`) |
| `.s-thin` | вспомогательная (1.2px, `--muted`) |
| `.s-dash` | пунктир акцентом (построение, разрез) |
| `.s-accent` | выделенная линия (2.4px, `--accent`) |
| `.s-node` / `.s-node-r` / `.s-node-a` | узел белый с обводкой / залитый / акцентный |
| `.s-fillw` / `.s-fillsh` | заливка тёплым / тенью |
| `.s-txt` / `.s-txt-w` / `.s-txt-m` | подпись обычная / белая на заливке / мелкая приглушённая |
| `.s-ar-a` / `.s-ar-m` | стрелка акцентом / приглушённая |

**Правила рисунка.** `viewBox` обязателен, `width` в атрибуте, `role="img"` + `aria-label` с человеческим описанием. Никаких чёрных `stroke="black"` — только классы, иначе рисунок не сядет в палитру.

### ⚠ Подписи внутри рисунка — почти нет (решение владельца 2026-07-16)

> **Внутри SVG живёт только математическая МЕТКА. Пояснение живёт в `figcaption`.**

- ✅ **метка** — имя объекта или координата: `C₁ = 1`, `v`, `t`, `0`, `−1`. Без неё график не читается.
- ❌ **пояснение** — фраза, объясняющая смысл: «одна из триангуляций каждого — растёт число способов, а не только вершин». Такое **некрасиво и непонятно** прямо в рисунке: набирается мелким, ломает композицию, конкурирует с картинкой. Всё это идёт в подпись под рисунком.

*Откуда правило.* В рукописных эталонах накопился перекос: 261 `<text>` на 28 рисунков, и часть — именно пояснения. Считаем это дефектом эталона, а не образцом: **эталон — источник правды по палитре и макету, но не по количеству подписей.**

*Как показать смысл без подписи.* Смыслом должна работать **графика, а не текст**: цвет (`.s-accent` = «то, что изменилось»), заливка узла (`.s-node-r` = «объект, о котором идёт речь»), пунктир (`.s-dash`/`.s-thin` штрихом = ось, построение). Пример: в рисунке действия `e_i` не написано, на какие точки оно действует, — **пара `i, i+1` просто залита**, и это видно сразу.

### Словарь примитивов (из чего рисуются наши иллюстрации)

Держим набор минимальным — рисовать должно быть **несложно**, поэтому все наши сюжеты (пути, дуги, состояния) собираются из шести кирпичей:

| Примитив | Как | Класс |
|---|---|---|
| **узел** ряда | `<circle r="3.4">` | `.s-node` (обычный) · `.s-node-r` (тот, о котором речь) |
| **дуга** между точками | `<path d="M x,y C …">` — полукруг; высота растёт с пролётом | `.s-line` · `.s-accent` (изменённая) |
| **дефект** / свободный конец | `<line>` вниз на 17px от узла | `.s-line` · `.s-accent` |
| **путь** (ломаная) | `<polyline points="…">`, шаг 36 по x, 26 по y | `.s-line` · `.s-accent` (результат) |
| **ось / уровень** | `<line>`, при нужде `stroke-dasharray="5 4"` | `.s-thin` |
| **стрелка** «переходит в» | `<line>` + `<path d="M…l9,4 -9,4 z">` | `.s-thin` + `.s-ar-m` |

**Сетка.** Шаг по x — 32–36px, по y — 26px, узел `r≈3.4`, полукруг поднимается на `14 + (пролёт−1)·11`. Панели «до → после» ставятся в один `<g transform="translate(0,N)">`, шаг между строками 68px.

### Как проверить рисунок глазами (в песочнице Cowork)

`cairosvg` **не применяет CSS-классы** — зальёт всё чёрным и соврёт. Для проверки развернуть классы в presentation-атрибуты и отрендерить:

```python
M = {'s-line':'fill="none" stroke="#211f1b" stroke-width="2" stroke-linecap="round"', ...}
s = re.sub(r'class="([a-z0-9 -]+)"', lambda m: " ".join(M[c] for c in m.group(1).split()), svg)
cairosvg.svg2png(bytestring=s.encode(), write_to='x.png', scale=2, background_color='#fbfaf6')
```
Дальше — **посмотреть PNG**. В самом документе классы работают, это костыль только для гейта. *(Пойман на первом же рисунке: без разворачивания classes путь залился чёрным и картинка выглядела катастрофой, хотя в браузере верна.)*

**Плейсхолдер.** Пока рисунка нет — `🖼 описание {N}`: dashed-врезка с «✎». Это не заглушка-отписка, а **запись долга**: видно, что здесь обязана быть картинка и какая.

## 7. Примитивы (решение владельца — тащим все четыре)

- **Портреты** (`--p-имя` = base64-JPEG в CSS-переменной, врезка `.ph` с подписью). Живут в проектном слое: универсален механизм, а не набор лиц.
- **Метро / лестница** (`.metro`, `.ladder`) — визуальная карта структуры: как части связаны. Прямо работает на §1, поэтому в ядре.
- **`data-source`** — атрибут блока с адресом происхождения: `data-source="mir1-skelet.md §2 [утверждение]"`. Глазом не виден, но делает вид **сверяемым с источником** и ловит дрейф.
- **Вкладки** (`.tabbar` + `.tab`) — несколько потоков в одном файле (8 лекций; рассказ ‖ скелет). Мосты между вкладками: `a[data-tab]` — пунктир + `↗`.

## 7½. ⚠ ГЕЙТ ВЫХОДА — обязателен после КАЖДОЙ сборки

```
python3 _generator/build_doc.py <src>            # линтер источника + сборка
python3 _generator/tools/check_view.py <src>     # ← ГЕЙТ: текст не съеден
```

**Зачем отдельный гейт.** Линтер `build_doc.py` проверяет структуру ИСТОЧНИКА, но не то, что увидит глаз. Инцидент 2026-07-16: в формуле стоял сырой `<` (`$a<b<c<d$`) — браузер прочитал `<b` как открывающий тег и **съел весь текст до ближайшего `>`**, то есть до конца блока. В markdown текст на месте, в HTML тоже — пропадает только при отрисовке. Владелец натыкался на это **регулярно**; глазами в источнике не ловится в принципе.

Гейт проверяет две вещи, обе валят сборку:
1. **опасная формула** — сырой `<` / `>` внутри `$…$`;
2. **хвост блока не виден в HTML** — конец каждого блока источника ищется в тексте выхода со снятыми тегами. Ловит ЛЮБОЕ съедание, не только случай `<`.

**Правило письма, вытекающее отсюда:** в формулах пишем `\lt` и `\gt`, а не `<` и `>`. KaTeX их понимает, в HTML угловая скобка не попадает.

## 8. Чего НЕ делаем

- Не заводим цвет/плашку, за которой нет типа блока. Новый вид — только вместе с новым типом в `STANDART-teksta.md`.
- Не расширяем колонку текста ради «плотности».
- Не пишем номера секций руками (§5).
- Не рисуем растром то, что рисуется SVG.
- Не тащим украшения из веба (тени, градиенты-фоны, иконки) — палитра уже устоялась, она скупая осознанно.
- Не пишем новый генератор (правило фабрики): вид собирается `_generator/build_doc.py`.
