### Шаг 1. ЗАМЕРИТЬ. Скриптом, не глазами

🔴 **Это не задача на вкус. Пиши одноразовый python-скрипт** (положи его в свою зону, `stdlib` + `re`, парсинг HTML регекспами допустим — деки машинно-порождённые и однородные) и получи таблицу **на каждый слайд каждого из четырёх деков**. Колонки — минимум эти:

| метрика | как считать |
|---|---|
| знаков видимого текста | текстовые узлы вне `<script>/<style>`, без разметки |
| текстовых блоков | абзацы + элементы списка + заголовки |
| иллюстраций | `<svg>`, `<img>`, `<canvas>`, `<figure>` |
| площадь МИНИМАЛЬНОЙ иллюстрации | по `width`/`height`/`viewBox`; в px² |
| 🔴 **текстовых узлов ВНУТРИ иллюстрации** | `<text>` внутри `<svg>` + подписи внутри `<figure>` |
| 🔴 **из них с КИРИЛЛИЦЕЙ** | `[а-яА-ЯёЁ]` внутри рисунка — владелец назвал это прямым запретом |
| семейств шрифтов на слайде | уникальные `font-family` в inline-стилях и классах слайда |
| сцен | по механике сцен движка (`SLIDE-FORMAT.md` скажет, как они помечены) |
| заголовок есть / нет | видимый заголовок слайда |

Отдельно, одним числом на дек: сколько всего уникальных `font-family`, сколько уникальных цветов в inline-стилях, сколько правил CSS не из общего ядра (per-slide scoped).

**Охват называй числом:** «обработано 23 из 23 слайдов buffon», и так по каждому деку. Слайд, который скрипт не разобрал, — в отдельный список «не разобрано», а не молча в ноль. *Почему: `promer.py` этой фабрики однажды печатал «slide N», нумеруя с нуля, и три захода спорили о разных слайдах под одним номером.*

### Шаг 2. НАЙТИ, ГДЕ РАСПРЕДЕЛЕНИЯ РАСХОДЯТСЯ

По каждой метрике сравни четыре дека: медиана, максимум, и **у скольких слайдов метрика хуже, чем худший слайд Бюффона**. Нас интересуют только те метрики, где Бюффон отличается от остальных **в одну сторону системно**, а не на одном слайде.

Гипотезы владельца, которые надо ПРОВЕРИТЬ, а не подтвердить (любая может оказаться ложной — так и напиши):
1. «на некоторых слайдах узкая полоса справа или снизу, забитая миллионом мелких картинок, на которых ничего не видно» — ищется как «много иллюстраций + маленькая минимальная площадь на одном слайде»;
2. «на иллюстрациях не должно быть букв, кроме коммутативных диаграмм» — ищется колонкой «кириллица внутри рисунка»;
3. «в Бюффоне правильно вложено количество индивидуальности и силы в каждый слайд» — проверяется числом per-slide scoped CSS-правил: если у Бюффона их системно больше, значит «индивидуальность» имеет машинное выражение, и это важнейший результат захода.

### Шаг 4. КЛАССИФИЦИРОВАТЬ каждое различие

Итоговая таблица `ETALON-DIF.md`. Одна строка = одно различие. Колонки:

`различие` · `чем доказано (число, а не мнение)` · `класс` · `адрес лечения`

Класс — ровно один из трёх, других не изобретать:
- **КОД** — падает в генераторе. Обязателен адрес: какой файл `_generator/`, какая проверка, и что именно она печатает при нарушении.
- **ПРАВИЛО ТЕКСТА** — машина проверить не может, но человек может по чеклисту. Обязательна формулировка чеклиста одной строкой.
- **РЕШЕНИЕ АВТОРА** — автоматизации не поддаётся вообще. Это законный класс и не признак неудачи: если различий этого класса окажется большинство, это и есть ответ, и он ценен.

**КРИТЕРИЙ ГОТОВНОСТИ (может ПРОВАЛИТЬСЯ):**
1. Файл `ETALON-DIF.md` существует; в нём пер-слайдовая таблица по **всем четырём** декам, и для каждого названо «обработано N из N слайдов», где N — реальное число слайдов в файле (проверяемо грепом по деку).
2. **Не меньше трёх различий класса КОД, у каждого — конкретный адрес в `_generator/` и текст сообщения, которое проверка напечатает.** Различие без адреса — не КОД, переклассифицируй честно.
3. По всем шести правилам G1–G6 отвечены оба вопроса шага 3. Шесть из шести, не «основные».
4. По каждой из трёх гипотез владельца — вердикт с числом, включая «гипотеза не подтвердилась, проверено N из N слайдов». **Отрицательный вердикт несёт охват в себе.**
5. Скрипт замера лежит в зоне и запускается повторно (`rc=0`), чтобы через месяц замер можно было повторить на новом деке.

Провалиться этот критерий может так: таблица есть, а различий класса КОД ноль или у них нет адресов — значит заход выдал эссе про дизайн вместо инженерного вывода, и приёмка его завернёт.
**Отрицательный вердикт несёт ОХВАТ В СЕБЕ:** не «дыр не найдено», а «дыр не найдено, проверено X из Y». Без охвата вердикт не принимается — «проверено 2 из 9» и «проверено 9 из 9» выглядят одинаково.

## 3. ВЕРИФИКАТОР — нужен, хотя ничего не двигаем

Операция не лоссовая, но **весь заход стоит на числах, а числа легче всего выдумать** — особенно когда таблица большая и красивая. Поэтому один свежий субагент, ДРУГИМ методом:

- берёт **пять слайдов, выбранных им самим** (не тобой) — минимум по одному из каждого дека;
- пересчитывает по ним твои метрики **не твоим скриптом**, а руками по тексту файла;
- отдельно проверяет самое важное: число текстовых узлов с кириллицей внутри иллюстраций на этих пяти слайдах;
- вердикт: «расхождений с таблицей 0» или список расхождений с адресами.

Расхождение нашлось — **не переписывай таблицу молча**: почини и назови в отчёте, что именно врал скрипт. *На этой фабрике верификатор однажды развернул два вердикта исполнителя на противоположные, и это единственный приём, который поймал настоящий дефект; но был и обратный случай — верификатор соврал сам, и исполнитель правильно его опроверг, проверив вручную. Если считаешь его вердикт неверным — опровергай, с доказательством в отчёте.*

Субагентов всего в заходе: **не больше 3** (по желанию — до 2 на параллельный замер деков, 1 верификатор). Рейт-лимит — отступить и доложить, не слепой ретрай.

## 4. 🔴 КОММИТ СВОЕЙ ЗОНЫ — ПОСЛЕДНИЙ ХОД ЗАХОДА, НЕ ОПЦИЯ
Ты работаешь host-side и в `.git` ПИШЕШЬ — значит коммитишь САМ, никому не передавая:
```
git --no-optional-locks add -- _studio/zhurnal/2026-07-30_dovodka-fabriki/                     # вводит НОВЫЕ пути в индекс
git --no-optional-locks commit -m "dovodka-fabriki волна A: <что сделано>" -- _studio/zhurnal/2026-07-30_dovodka-fabriki/   # отсекает всё чужое
python3 _generator/tools/git_zona.py check --zone _studio/zhurnal/2026-07-30_dovodka-fabriki/   # из корня репо; должен быть ✅
git --no-optional-locks show --stat                        # обязаны быть ТОЛЬКО твои пути
```
🔴 **ОБА хода обязательны, ни один не лишний** (полное «почему» и цена — `../docs/kak-delat/GIT-disciplina.md §3`):
- **`add`** — pathspec-коммит знает только **отслеживаемые** пути; новый файл без `add` даёт `did not match any file(s) known to git`.
- **`-- <пути>` в самом `commit`** — иначе `commit` забирает индекс ЦЕЛИКОМ, вместе с чужим, застейдженным кем угодно рядом с тобой (репо `materials/` общий, писателей трое). *Обе половины оплачены 21.07 в один вечер: голый `commit` подмёл чужой индекс — коммит на 89 файлов вместо трёх; «починка», убравшая `add`, завалила все 10 коммитов повторно.*
⚠ **Хук `pre-commit` покраснел — сначала посмотри, на ЧЬИХ путях.**
- Красное на ТВОИХ путях (новый `.md` не зарегистрирован в `../../docs/KARTA.md §6`, битая ссылка) — **чини, не обходи**: там только твоё, обходить нечего.
- Красное на ЧУЖОМ, унаследованном долге (ворота дают сотни ❌ старых нарушений) — законный обход, но ТОЛЬКО с причиной; голый `--no-verify` инструмент отклонит, а причина сама уедет в `INCIDENTY.md`:
```
python3 _generator/tools/git_zona.py commit --zone _studio/zhurnal/2026-07-30_dovodka-fabriki/ \
    --no-verify "чужой долг: <что именно покраснело>" -m "<что и зачем>" --push
```
Ту же причину назови отдельной строкой отчёта долгом. *Урок 9: обход был законен по канону и не существовал в инструменте — первый же коммит владельца встал на чужом долге.*
**Коммит не прошёл по ВНЕШНЕЙ причине** (чужой лок, конфликт, detached HEAD) — чужое состояние репозитория НЕ чини: зафиксируй файлы и напиши в отчёт отдельной строкой «коммита нет, причина такая-то, нужно ваше действие».
