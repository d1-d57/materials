  ## 4. UX ввода для детей 8–9 лет
  
  - **Touch targets**: минимум 1×1 см (0.4×0.4 дюйма) — физическая оценка по ширине пальца (1.6–2 см), плюс раздельность ≥2 мм между целями (одного размера мало, если targets слеплены). Для маленьких детей (дошкольники) рекомендуют 2×2 см, но это преимущественно про ранний возраст. Источник: https://www.nngroup.com/articles/touch-target-size/
  - **8–9 лет конкретно**: моторика уже прилично развита (могут переключаться между инструментами по ходу задачи), НО drag-and-drop на большое расстояние по-прежнему сложен — дети хуже справляются с точным перетаскиванием «в узкий коридор» или в точную точку, предпочитают мышь трекпаду для drag. Рекомендация NN/G — для этого возраста предпочитать простые клики/клавиатурный ввод перетаскиванию сложных траекторий. Это прямо поддерживает ваше решение «палитра значений + клавиатура + прощёлкивание» вместо drag-n-drop в судоку/футошики. Источник: https://www.nngroup.com/articles/children-ux-physical-development/
  - **Подсветка конфликтов в судоku/футошики** — рецензируемых исследований именно про детей 8–9 лет я не нашёл (это ниша, где решения принимаются по опыту, не по РКИ). Логика из общей эмпирики ИТС переносима: подсветка конфликта — это, по сути, immediate step-level feedback (как в model tracing), а не answer-only — согласно VanLehn это полезнее, чем узнать об ошибке только в конце. НО подсветка конфликта одновременно снижает нагрузку на самостоятельный поиск ошибки (это уже подсказка/scaffolding, а не чистая тренировка внимания) — компромисс: включать подсветку только ПОСЛЕ первой неверной попытки на клетке (что соответствует уже принятому правилу «после ошибки можно перерешать, но без звезды») — так подсветка не обесценивает первую самостоятельную попытку.
  
  ## 5. Вёрстка «один экран без прокрутки»
  
  - **Классическая техника** — сцена фиксированного дизайн-разрешения (например, 1280×720 или 16:9-контейнер) вычисляется `scale = Math.min(availableWidth/designWidth, availableHeight/designHeight)`, применяется `transform: scale()` к корневому контейнеру — контент масштабируется пропорционально без искажений, с леттербоксингом по одной из осей. Это надёжнее, чем чистый `vw/vh` layout, потому что гарантирует «один экран = одна страница» на любом соотношении сторон ноутбука. Источник: https://css-tricks.com/scaled-proportional-blocks-with-css-and-javascript/
  - Дополняющие современные CSS-инструменты (без отдельного эмпирического источника, но общепринятая практика): `clamp()` для текста/отступов, чтобы контент тянулся без ручных медиа-запросов; container queries — чтобы карточка/панель внутри сцены реагировала на свой контейнер, а не на весь viewport (полезно при разных панелях на разных «листках»); `aspect-ratio` для резервирования пропорций блоков до загрузки контента.
  - **Тестирование** — из первого источника следует практическая рекомендация: тестировать на нескольких реальных соотношениях сторон ноутбуков (16:9, 16:10, 3:2) и на маленьком (11″) экране — граничные случаи масштабирования проявляются именно там, где `availableHeight` резко меньше `designHeight`.

  9. **Индикатор прогресса по листку** (сколько пунктов пройдено из скольких) — снижает тревожность «сколько ещё». Сложность: малая.
  10. **Доступность**: контраст, размер шрифта увеличиваемый, обязательно крупные touch targets (см. п.4) — важно даже для мышки/трекпада на ноутбуке. Сложность: малая.
  11. **Idle-детекция для статистики репетитора** (см. п.3) — таймер бездействия, чтобы отличить «думает» от «отвлёкся». Сложность: малая.

**Как теперь устроена проверка:**
- **Разложения** засчитываются любые верные: можно разбивать как первое, так и второе число. Подгонку «20 · 20 + 5 · 0 = 400» проверка по-прежнему не пропускает.
- **Числа** сравниваются по значению: «0450», «2 000» и «2000» засчитываются.
- **Множества** можно писать через любые разделители: «9; 4», «1, 4, 6, 7, 9» и «{4;9}» — всё засчитывается.

**Головоломки** больше не обязательны: на судоку и футошики стрелка «дальше» открыта сразу, их можно пролистать.
