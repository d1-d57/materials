# ZHURNAL — хроника поломок git и того, чем они закрыты

> Одна запись = одна поломка. Формат: **что сломалось · настоящая причина · чем закрыто (механизм) · ЦЕНА**.
> Правила отсюда НЕ читают — они в каноне `../../docs/kak-delat/GIT-disciplina.md`. Здесь память: почему канон такой и что уже пробовали.
> **Дата данных каждой записи — в её заголовке.** Запись задним числом не переписывается: неверный диагноз честнее пометить как опровергнутый, чем затереть.
> **Сырые симптомы сюда не носят:** с 23.07 неуспешный `commit` САМ пишется в `INCIDENTY.md` (канон §0б). Сюда — только переваренное: урок с ценой; в строке INCIDENTY тогда ставится `→ ZHURNAL`.

## 2026-07-21 — сессия 1. «Каждый раз куча проблем с этим коммитом»

**Повод.** За одну сессию арки `2026-07-21_mat-kostyak` работа ТРИЖДЫ не доехала в git; в дереве хронически висело 120+ путей. Владелец: «каждый раз куча проблем».

### 1.1. Гейт сам ронял коммиты владельца
`ARKA §6` предписывал Cowork гонять `git status --short`. Обычный `git status` НЕ read-only — он переписывает индекс и берёт `.git/index.lock`. Механизм, следивший, чтобы работа не терялась, отбирал лок у владельца ровно в момент ручного коммита.
**Закрыто:** `--no-optional-locks` во всех вызовах, безусловно; вся работа с git — через `git_zona.py`.
**ЦЕНА:** три сорванных коммита за сессию.

### 1.2. Коммит ехал по самому дырявому каналу фабрики
Cowork в `.git` не пишет ⇒ выдавал владельцу блок `&&` в чат ⇒ это хенд-офф, а по статистике самой фабрики хенд-офф даёт 0 из 8. Обрыв цепочки `&&` посередине невидим.
**Закрыто:** план файлом (`_studio/.commit-plan`) + одна неизменная команда `git_zona.py commit --push`. Владелец не собирает команды. ⚠ **`--push` дописан 23.07:** без него канон противоречил сам себе (§1 предписывал владельцу `--push`, §2 велел Cowork выдавать команду без него) — и три коммита застряли на машине владельца.
**ЦЕНА:** 17.07 коммита не было ЧАС при живой параллельной работе; владелец добросовестно считал, что закоммитил.

### 1.3. Гейт «работа доехала в git» стоял слишком поздно
Жил только на хэндоффе чат→чат; между заходами проходило несколько приёмок.
**Закрыто:** гейт 0 на приёмке КАЖДОГО отчёта (`RUKOVODSTVO §Приёмка`) + строка `КОММИТ:` с хэшем в шаблоне отчёта.

### 1.4. Свальный коммит: 89 файлов вместо трёх
`git commit -m` без pathspec забирает индекс ЦЕЛИКОМ, вместе с чужим застейдженным.
**Закрыто:** форма `add -- <пути>` + `commit -- <пути>`; обе половины под фикстурой.
**ЦЕНА:** коммит на 89 файлов; план из 10 коммитов схлопнулся в один свальный.

### 1.5. «Починка», убравшая `add`, завалила все 10 коммитов
Pathspec знает только ОТСЛЕЖИВАЕМЫЕ пути; новых в плане было три четверти.
**Закрыто:** там же — оба хода обязательны, фикстура краснеет на снятии любого.
**ЦЕНА:** 125 путей остались вне git; владелец получил вторую простыню отказов подряд.

### 1.6. 🔴 ОПРОВЕРГНУТО: «в репозитории живёт авто-коммит»
Несколько разборов (и уроки арки `mat-kostyak`) объясняли грязный индекс авто-коммитом. **Его нет и не было**: единственный хук `.githooks/pre-commit` гоняет `check_uroki.py` и не стейджит; ни cron, ни launchd. Индекс грязнят живые писатели через общий индекс.
**Почему это важно:** из фантома вывели закон «НИКОГДА `add` → `commit`», который воспроизводил поломку 1.5 — при том что рабочий инструмент делает именно `add` → `commit`.
**Урок:** правило, которому противоречит его единственная реализация, — не правило, а описка.

### 1.7. Моя фикстура записала мусорный коммит в боевой репозиторий
Внутри хука git экспортирует `GIT_DIR`/`GIT_INDEX_FILE` **абсолютными** путями; фикстура создавала репо в `/tmp`, но её `add`/`commit` шли в НАСТОЯЩИЙ индекс. Вне хука была зелёной — ловушка открывалась только при наследовании окружения.
**Закрыто:** `unset $(git rev-parse --local-env-vars)` первым ходом фикстуры (каноничная форма из документации githooks) + `env -u` в хуке вторым слоем.
**ЦЕНА:** коммит `295d051` автором `fixture <fixture@test>`, перезаписанная git-личность владельца, три залипших лока.
**Урок:** гейт — тоже код, и он опаснее проверяемого. Проверять его надо В ТЕХ условиях, где он сработает.

### 1.8. Развилки, закрытые на живых файлах (не переоткрывать без нового мотива)
- **Разрез монорепо на отдельные git-папки — ОТКЛОНЁН.** `VNESHNIE-RESURSY.md` держит 6 адресов через `../`; `_generator/` и `_studio/` общие для 11 проектов. Дал бы пять грязных деревьев вместо одного и сегодняшнюю проблему не предотвратил бы.
- **Снапшоты (`*/snapshots/`) и библиотечные pdf — вне git.** 18 tar-архивов на 265 МБ + 145 pdf на 333 МБ. Правило: файл «делается» командой или скачиванием ⇒ в git его нет.
- **`ucheniki/` (67 файлов) впервые закоммичен** — был зарегистрирован в `README`/`KARTA`, но НИ ОДНОГО файла не было в git.

### 1.9. Параллельные заходы: канон предписывал гонку
Канон говорил «параллельным заходам — РАЗНЫЕ ветки». Но у репозитория ОДНА рабочая папка на все ветки: `git checkout` одного захода подменяет файлы под ногами другого.
**Закрыто:** `git_zona.py worktree add` + `bootstrap_zahod.py --worktree` (вписывает `cd` вместо `checkout`, развилку решает генератор).
**Статус:** ⚠ в бою не проверено — см. `SOSTOYANIE.md`.

## 2026-07-22/23 — сессия 2. «Опять не коммитится»

### 2.1. 🔴 Cowork коммитил из песочницы — репозиторий вставал для всех
В песочнице Cowork запрещён `unlink` во ВСЁМ монтировании. Git при любой записи создаёт временные файлы и удаляет их — удалить не может, они остаются минами.
Проверено на одноразовом репо ВНУТРИ того же монтирования:
- `commit -- <pathspec>` → `next-index-<PID>.lock`, `index.lock`, `HEAD.lock`; следующий git падает `File exists` (PID мелкие, переиспользуются);
- обычный `commit` без pathspec → мин меньше, но `HEAD.lock` и `tmp_obj_*` остаются **всё равно**;
- `GIT_INDEX_FILE` в `/tmp` **не помогает** — git всё равно кладёт `next-index` внутрь `.git`.
⇒ «другая форма коммита» тему не решает. Cowork в песочнице — НЕ коммитер.
**Закрыто:** детект FUSE-монтирования; `commit`/`clean`/`untrack`/`worktree add|drop` **отказываются работать** из песочницы и печатают команду владельцу. Чтение работает.
**ЦЕНА:** репозиторий дважды вставал примерно на полчаса; снять лок из песочницы нечем — каждый раз требовался владелец. Коммит при этом технически СОЗДАВАЛСЯ — оттого соблазн «ну прошло же».

### 2.2. `doctor` не видел самого частого блокера
Смотрел ровно `index.lock`, а висели `next-index-15.lock`, `next-index-22.lock`, `HEAD.lock`.
**Закрыто:** показывает ВСЕ локи с возрастом + отдельно считает мусорные `tmp_obj_*`.
**ЦЕНА:** два цикла диагностики вслепую.

### 2.3. Уборка убивала процесс ПОСЛЕ успешного коммита
`PLAN.unlink()` без защиты бросал `PermissionError` уже после успеха — человек видел traceback под словом «✅».
**Закрыто:** `try/except`, успех печатается ДО уборки; при падении `commit` показывает строки, похожие на ошибку, а не первую попавшуюся.

### 2.4. 🔴 Корень системной боли: Cowork выдавал владельцу SHELL
Команды пишутся в bash/Linux (песочница), исполняются в zsh/macOS. Ломается систематически, и каждый раз выглядит как «git опять не работает»:

| Что | Как сломалось | Когда |
|---|---|---|
| `rm -f .git/*.lock` | в zsh несовпавший glob роняет ВСЮ строку (`no matches found`) — уборка не выполнилась, а выглядела выполненной | 22.07 |
| `cd /sessions/...` | путь песочницы; у владельца такого нет → `fatal: not a git repository` | 11.07 и 22.07 |
| цепочка `&&` | обрыв в середине невидим | 17.07 |
| `xargs -0/-r` | BSD ≠ GNU | 21.07 |
| `$(git ls-files …)` | пути с пробелами (`kurs leto 2026/**`) расщепляются | 17.07 |

**Закрыто (закон §0 канона):** Cowork не выдаёт shell вообще — только `python3 git_zona.py <команда>`. Нет нужной операции — добавляется подкоманда, а не строчка в чат. Так родились `clean` и `untrack`.

### 2.5. GNU-изм в фикстуре остановил здоровый коммит владельца
В фикстуре `clean` стояло `touch -d '10 minutes ago'` — GNU-синтаксис. На macOS BSD-`touch` его не понимает, fallback создал файл с текущим временем, лок посчитался свежим, проверка покраснела. У Cowork в Linux было зелено.
**Закрыто:** возраст ставится через `python3`; добавлена ловушка, ищущая GNU-измы во всех фикстурах и хуках; правило вписано в §0 канона.
**ЦЕНА:** остановлен здоровый коммит владельца.
**Урок:** гейт, зелёный у автора и красный у владельца, хуже отсутствующего гейта. Правило про shell касается и КОДА, исполняемого у владельца, а не только команд в чат.

### 2.6. Итог сессии 2 — что стало механизмом
`git_zona.py`: `doctor` · `check` · `plan` · `commit --push` · `clean` · `untrack` · `worktree`. Семь ловушек в фикстуре, все проверены мутацией. Отдельная ловушка следит, чтобы канон не отстал от инструмента.

### 2.7. Инструмент напугал владельца УСПЕХОМ — «❌ Плана нет» после сработавшего коммита
Первый же коммит новой арки прошёл (`0b17189`). `commit` при успехе сам удаляет план — и повторный запуск той же команды напечатал `❌ Плана нет: _studio/.commit-plan`. Владелец прочитал это как «коммит не сработал» и вернулся с «такая вот ирония судьбы», хотя всё было закоммичено минутой раньше.
**Настоящая причина:** сообщение не различало два разных состояния — «Cowork не написал план» (беда) и «план уже исполнен» (норма). Ошибочный ❌ на здоровом репозитории.
**Закрыто:** `commit` без плана смотрит на дерево. Чисто → `✅ коммитить нечего, последний коммит такой-то`, **rc=0**. Грязно → спокойная подсказка «собери plan; если это чужая зона — так и надо», rc=1.
**ЦЕНА:** ложная тревога владельца и лишний круг разбора. Прямых потерь нет.
**Урок (третий раз за две сессии, разными способами):** **инструмент, который печатает ❌ на нормальном исходе, обучает не доверять своим же гейтам.** Раньше в эту же яму падали: зелёное на упавшей проверке (`PRIEMKA.sh`), красное на здоровом документе (`check_view.py`), теперь красное на успешном коммите. Сигнал обязан отличать «сломалось» от «делать нечего».

## 2026-07-23 (вечер) — сессия 3. «Сохранить зону» стоило ритуала: пять срывов за вечер

**Повод.** Пять разных срывов коммита за вечер на стыке «Cowork готовит → владелец жмёт» (сырьё — `kod_commit-ux.md §2`). Диагноз: не пять багов, а ОДИН класс — путь «сохранить зону» многошаговый (2–3 команды + ручная правка файла + верный каталог + чистый argv), и каждый шаг — точка отказа. Инварианты при этом верные; лечилась ОБЁРТКА (`kod_commit-ux` — весь заход). Планка починки — не безотказность, а 100% наблюдаемость: happy-path одной командой, каждый отказ громкий, человеческим языком, с автоследом.

### 3.1. Запуск из `~` — инструмент даже не загрузился
`python3 _generator/tools/git_zona.py …` из домашней папки: питон не нашёл файл по относительному пути. Инструмент не запущен — подсказать не может; для владельца неотличимо от «git опять сломан».
**Закрыто:** тропа выдаётся с АБСОЛЮТНЫМ путём к инструменту (канон §1, §2) — каталог запуска безразличен (репо выводится из `__file__`, не из cwd).
**ЦЕНА:** два срыва подряд, минуты на ложный диагноз.

### 3.2. Хвост-«комментарий» уехал в argv
Cowork дописал в команду `# предпросмотр`; у владельца zsh без `interactivecomments`, `#` и слово после ушли программе. Argparse упал питоновым `unrecognized arguments: #` — ни что случилось, ни что делать.
**Закрыто:** `parse_known_args` + отказ человеческим языком («это хвост-комментарий из zsh, убери всё после кавычки») + автослед в INCIDENTY. Держится живым прогоном; сообщение — в фикстурной цепочке тропы.
**ЦЕНА:** обе `adopt`-команды подряд; владелец снова читал это как «git не работает».

### 3.3. Двухшаговость `plan → commit` не была очевидна
`commit` без `plan` — «Плана нет». Что путь двухшаговый, знал инструмент, но не владелец.
**Закрыто:** однокомандная тропа `commit --zone <з> -m "<что и зачем>" --push` — план для типового случая не нужен; отказ «плана нет при грязном дереве» теперь сам называет тропу первой подсказкой и логируется в INCIDENTY.
**ЦЕНА:** сорванный коммит + круг разбора.

### 3.4. Заглушка `==` в плане: сообщение должен вписать один, а жмёт другой
`plan` пишет `== <переписать>`, `commit` справедливо отказывает. Но вписать сообщение должен Cowork (текст у него), а коммитить может только владелец — стык не был оформлен ни одной тропой, и владелец про шаг «впиши сообщение» не знал.
**Закрыто:** в тропе сообщение живёт В САМОЙ КОМАНДЕ, которую Cowork выдаёт готовой — стык исчез как класс. Пустое или плейсхолдерное `-m` — человеческий отказ (ловушка в фикстуре). План-путь с заглушками остаётся для пакета РАЗНЫХ коммитов.
**ЦЕНА:** сорванный коммит; владелец узнал о шаге из отказа гейта.

### 3.5. `adopt` был в инструменте, но не в каноне — хук блокировал сам инструмент
Подкоманда `adopt` (лечение тени после worktree-захода) висела незакоммиченной: фикстура «канон отстал» краснела, pre-commit не пропускал коммит `git_zona.py`.
**Закрыто:** `adopt` дописан в канон (§4 — когда нужен, §5 — таблица); фикстура зелёная; закоммичено вместе с инструментом (`d41ebef`).
**ЦЕНА:** правка инструмента сутки жила только в рабочем дереве — одна смерть диска, и её нет.

### 3.6. Класс 4: память о поломке жила дисциплиной, а не механизмом
Отчёт о пяти срывах выжил случайно — был вшит в файл-заход; случись это в чужом чате, исчез бы бесследно. «Пиши отчёт о поломках» — правило, при нарушении которого ничто не краснеет ⇒ оно нарушается молча (`KONSTITUCIYA §11`). Девять прошлых поломок разбирались по памяти чатов.
**Закрыто:** НЕУСПЕШНЫЙ `commit` сам дописывает строку в `INCIDENTY.md` (симптом + подсказка + статус; дедуп за день, чтобы не шумело) — поведение единственной двери к git, работает во всех чатах у всех троих писателей. Разводка: INCIDENTY — сырая корзина, ZHURNAL — уроки с ценой. Держится ловушкой «убрал автозапись — красная».
**ЦЕНА:** прямых потерь в этот раз нет — и это случайность, а не заслуга: сырьё выжило только потому, что аналитик вшил его в заход.

### 3.7. Итог сессии 3
`commit --zone -m` — однокомандная тропа с общим ядром `execute_commits` (add+pathspec, лок, сверка — в одном месте у обоих путей); человеческий argv-диагноз; автолог INCIDENTY. Фикстура: 11 ловушек (+3 новые, все промутированы). Боем не проверено: тропа, INCIDENTY (см. `SOSTOYANIE §хвосты`).

## 2026-07-23 (ночь) — сессия 4. Кривой вход фабриковал мусор, а «пометка удалить» не удаляла

**Повод.** `bootstrap_arka.py --help` принял флаг за имя арки и **молча** создал папку-сироту `_studio/zhurnal/--help/` со скелетом; untracked, и каждый `git_zona.py plan` тянул её в черновик коммита вперемешку с настоящим. Рядом — устаревший дубль `ZAPROS-fable-2-vneshnie.md`, помеченный к удалению в HANDOFF, но не удалённый. Два корня арки в новой арене (bootstrap + гигиена): №1 «на кривом входе инструмент обязан ГРОМКО падать, а не тихо делать не то» (флаг проглочен как данные); №2 мета-корень «пометка ≠ механизм».

### 4.1. `bootstrap_*` глотали имя-флаг как данные
`bootstrap_arka.py` брал `argv[0]` сырым, без argparse и без валидации: `--help` стал именем арки и папкой на диске. `bootstrap_zahod.py`/`bootstrap_lekcia.py` на argparse отбивали голый `-x`, но не пустое / со слэшем / с ведущей точкой (argparse отдаёт их позиционному аргументу).
**Закрыто:** `validate_slug` отвергает ведущий `-` / пустое / пробелы / слэши / ведущую точку через `SystemExit` ДО любой записи; вызван в трёх скриптах (arka — на `slug`, zahod — на `a.tema`, lekcia — на `target.name`). Дублирован сознательно: общий модуль лёг бы вне зоны заходов. Держится ловушкой 14 (import + временные каталоги, чтобы гейт не писал в боевой репо — урок 1.7).
**ЦЕНА:** папка-сирота `--help` со скелетом на диске; каждый `plan` тянул её в черновик — кто-то вручную выцеплял мусор из плана каждую коммит-сессию; 23.07 она чуть не уехала в гейт-коммит `_studio`, поймал только ручной просмотр.

### 4.2. Подозрительный untracked входил в план сам
`plan`/`check`/`doctor` не отличали мусор от честной работы — путь с ведущим `-` шёл в черновик наравне с настоящим.
**Закрыто:** карантин — строгая эвристика «какой-либо компонент имени с ведущим `-`» (ноль ложных: легитимной арки/файла с таким именем не бывает), только для untracked (`??`). `plan` НЕ кладёт такой путь в `.commit-plan` и выносит отдельным блоком; `check`/`doctor` называют его отдельно от честного «вне git». Держится ловушкой 12.
**ЦЕНА:** та же регулярная — ручная выемка мусора из плана каждую сессию (прямых потерь в этот раз нет).

### 4.3. «Пометка удалить» не удаляет; а `rm` спотыкается о ведущий дефис
Дубль `ZAPROS-fable-2-vneshnie.md` был помечен к удалению в HANDOFF («удалить в Finder»), но заметка — не механизм, и он лежал. Снести его shell'ом владельцу не выдашь: имя вида `--help` начинается с `-`, `rm` примет за флаг (нужен `rm -- --help`) — ровно ловушка §0 (shell-в-чат ломается о zsh).
**Закрыто:** подкоманда `git_zona.py purge` снимает untracked-мусор без shell (Python `shutil`/`unlink`): предпросмотр без `--yes`, снос по `--yes`, из песочницы отказ (rc=3), неуспех сам в `INCIDENTY`. 🔴 Инвариант безопасности: трогает ТОЛЬКО untracked (проверка `git ls-files`) и только внутри репо; тронутое = названное РОВНО, ни файлом больше. Цели — явные пути или карантин-список `plan`. Обкатано на ЖИВОМ мусоре host-side: `--help/` (карантин) и `ZAPROS-fable-2-vneshnie.md` (явный путь) сняты, рабочий `fable_zapros-2-vneshnie.md` (отслеживаемый) и остальные 15 файлов арки целы. Держится ловушкой 13 (untracked-only + tracked-guard + sandbox-отказ, каждая половина мутацией).
**ЦЕНА:** мусор пережил свою пометку — «удалить» в HANDOFF ничего не удалило, дубль лежал до механизма.
**Урок (мета-корень арки, снова):** пометка ≠ механизм — тот же закон, что «правило без того, что покраснеет» (`KONSTITUCIYA §11`). «Удалить» без сущности, которая удалит, — надежда, а не действие; теперь удаляет `purge`.

### 4.4. Итог сессии 4
Укреплена ОБЁРТКА, ядро-инварианты не тронуты (проверено поимённо, 7 из 7: sandbox-отказ · pathspec+add · `--no-optional-locks` · граница `--zone` · тропа `-m` · автолог `INCIDENTY` · хук уроков). Фикстура: +3 ловушки (12 карантин, 13 purge, 14 bootstrap-валидация), все промутированы — снятие защиты краснит. Боем: `bootstrap`-валидация и `purge` проверены на живом мусоре host-side (реальные `--help/` и дубль сняты, рабочее цело); карантин — на одноразовом репо и на живом дереве (preview показал ровно цель). Свежий верификатор с пустым контекстом атаковал инварианты отдельным проходом.
⚠ Остаточный зазор (в отчёт, не в канон): pre-commit-хук поднимает `PROGNAT.sh` только при правке `git_zona.py`; ловушка 14 на `bootstrap_*` живёт в той же фикстуре, но при правке ТОЛЬКО `bootstrap_*` не гейтится. Хук вне зоны захода — не трогал.

## 2026-07-28 — сессия 5. Лекарством была ПРОЗА, и она не переносилась на следующий инструмент

**Повод.** Не новая поломка, а разбор их общего корня. За четыре сессии ~15 поломок инфраструктуры свелись к ОДНОМУ классу, который возвращался в новых аренах: `git_zona` → фикстуры → `bootstrap_*` → `purge`. Каждый раз класс закрывали ПРОЗОЙ — строкой канона, уроком в этом дневнике, пометкой в заходе. Проза лечит тот инструмент, на котором её написали, и не переносится на следующий: она лежит там, куда исполнитель с пустым контекстом не заглядывает, а он приходит с пустым контекстом всегда.

### 5.1. У гейта триггер был УЖЕ его собственного охвата
Живое доказательство корня, названное ещё в `§4.4` как «остаточный зазор» и пролежавшее пять дней: хук поднимал `fixtures/git_zona/PROGNAT.sh` ровно при правке `git_zona.py` — а ловушка 14 внутри этой фикстуры сторожит `validate_slug` во ВСЕХ трёх `bootstrap_*`. Правишь `bootstrap_arka.py`, снимаешь валидацию — фикстура, которая это ловит, не запускается. Охват жил в голове автора фикстуры, триггер — в `grep` хука, и они разошлись молча.
**Закрыто:** фикстура ОБЪЯВЛЯЕТ охват строкой `# TOOL-CONTRACT-COVERS: <файлы>` в шапке; линтер и хук читают её, а не догадываются. Мутация: снял строку — фикстура перестаёт подниматься, и мета-фикстура краснеет.
**ЦЕНА:** зазор был ЗАМЕЧЕН и ЗАПИСАН 23.07 — и всё равно прожил пять дней, потому что запись сама по себе ничего не поднимает. Это и есть цена прозы в чистом виде: тот же класс, что «пометка ≠ механизм» (`§4.3`), но уже на самом гейте.

### 5.2. Правила инструмента держались памятью исполнителя
`--no-optional-locks` на каждом вызове git, никаких GNU-измов, никакого сырого shell владельцу, пишущая операция под sandbox-отказом — всё это канон, и всё это соблюдалось ровно настолько, насколько очередной агент дочитал `GIT-disciplina`.
**Закрыто:** `check_tool_contract.py --staged` — статический гейт над `_generator/tools/*.py`, пять проверок, в хуке на КАЖДЫЙ правленый инструмент. Судит staged-диф (чужой долг чужой коммит не валит), молчит когда чисто, проверяемый инструмент НИКОГДА не исполняет — только текст и AST. Послабления не спрятаны в смягчённой проверке, а названы списком `fixtures/tool_contract/BASELINE`. Держится мета-фикстурой: 21 утверждение, каждая из пяти проверок промутирована в ОБЕ стороны (снял проверку — красное; здоровый образец — зелёное).
**ЦЕНА:** класс возвращался КАЖДУЮ сессию новой ареной — четыре сессии подряд. Последняя цена (`§4.1`): `bootstrap`-мусор `--help/` чуть не уехал в гейт-коммит `_studio`, поймал только ручной просмотр плана.

### 5.3. Калибровка сразу нашла две живые дыры — и это лучший аргумент за механизм
Прогон нового гейта по всем 10 инструментам: 8 зелёных, 2 красных, и оба красных — НАСТОЯЩИЕ нарушения канона, а не ложные срабатывания. `check_uroki.py:82` зовёт git без `--no-optional-locks` — из `pre-commit`, то есть при каждом коммите всех троих писателей. `git_zona.py:338` печатает владельцу `cd … && rm -f .git/*.lock && find …` — цепочку с glob, ту самую конструкцию из таблицы цен `§0`, взамен которой и заводилась подкоманда `clean`. Обе вне зоны захода, обе описаны в `SOSTOYANIE §хвост 00`, чинятся одной строкой каждая.
**ЦЕНА:** обе дыры прожили в репозитории всё время, пока правило про них существовало ПРОЗОЙ в каноне — который читали и на который ссылались. Проза была написана, прочитана и не соблюдена одновременно.

### 5.4. Гейт над гейтами едва не ударил по своим — дважды, и оба раза поймано до репо
Первая калибровка дала 15 красных, вторая 73: линтер краснел на собственном перечне запрещённого в докстринге, требовал sandbox-защиту от читающих `check_*.py` (по строке `"/.git/"` в списке ИСКЛЮЧЕНИЙ), и принимал обратный апостроф markdown-цитирования за подстановку shell — 60+ ложных на ровном месте. Все три смягчены по правилу «краснит на здоровом → кривая проверка, а не кривой инструмент». Третью поймал уже живой прогон хука: дословный `touch -d` в тестовых данных новой мета-фикстуры покрасил ЧУЖУЮ фикстуру (ловушка 7 грепает все `fixtures/*/PROGNAT.sh`) и заблокировал бы каждый коммит, трогающий `git_zona.py`; образцы-нарушители теперь собираются из половинок.
**ЦЕНА:** прямых потерь нет — все три пойманы до коммита. Но цена показана: **гейт опаснее того, что он проверяет**, и «фикстуры зелёные» без прогона В ТЕХ УСЛОВИЯХ, где гейт сработает (внутри хука, с наследованным окружением), — недоказанный вердикт. Ровно предупреждение `GIT-disciplina §5`, подтверждённое на четвёртом собственном примере.

### 5.5. Верификатор снял с гейта два дефекта, каждый из которых убивал затею молча
Свежий субагент с пустым контекстом атаковал гейт (23 судимых файла, 9 нарушителей, 5 сценариев уровня хука) и нашёл ДВА дефекта, которых не видно ни на фикстурах, ни на калибровке:
- **Линтер читал рабочую копию, а не staged-блоб.** Застейджил нарушителя, поправил файл на диске — гейт зелёный, а в коммит уезжает нарушитель. «Поправил после `add`» — рутина, а не трюк. Гейт врал ровно в ту сторону, ради которой заводился.
- **Судил файл целиком, а не добавленные строки.** Формально это соответствовало ТЗ («пока файл не правят»), но на живом дереве уже лежали две пре-существующие дыры — и `git_zona.py`, самый правимый инструмент репозитория, становился незакоммитабельным без `--no-verify` **с первого дня жизни гейта**, из-за строки, которой правящий не касался.

**Закрыто:** линтер судит `git show :<путь>` и фильтрует нарушения по строкам из `diff --cached -U0`. Проверено на одноразовом репо: безобидная правка `git_zona.py` и `check_uroki.py` проходит, нарушение в ДОБАВЛЕННОЙ строке краснеет, починка на диске после `add` гейт не обманывает. Заодно закрыты формы, которые верификатор провёз не хитростью, а обычным стилем: GNU-изм, разнесённый по элементам списка (`["sed","-i",…]` — сплошной строкой в питоне так не пишут, а регексп видел только сплошную), команда шеллу строкой (`os.system("git commit …")` — мимо обеих проверок), `.py` в подпапках `tools/`, GNU-изм в `.sh`, вычистка `GIT_ZONA_REPO`/`TOOL_CONTRACT_HOME` в хуке (обе молча выключали гейт целиком), объявление охвата подделкой строки внутри heredoc. И три ложных срабатывания: `.remove()` у обычного списка, сборка команды из кусков `["git"] + FLAGS`, прозаическое «никогда не набирай `rm -rf` вручную».
**ЦЕНА:** оба дефекта дожили до конца захода, пройдя мимо 21 утверждения мета-фикстуры, — потому что фикстуру писал тот же, кто писал проверки, и она проверяла ровно ЛИТЕРАЛЬНУЮ форму каждого нарушения. Верификатор с пустым контекстом стоил ~10 минут и снял дефект, который сделал бы гейт зелёным на коммите с нарушителем внутри. Это подтверждает `GIT-disciplina §5` буквой: **гейт опаснее проверяемого, и «фикстуры зелёные» без независимой атаки — недоказанный вердикт.** Мета-фикстура доросла с 21 утверждения до 33.

### 5.6. Итог сессии 5
Механизмом закрыт эпистемический корень, а не очередная арена. Три прежних гейта не тронуты и проверены живыми (урок без ЦЕНЫ, `.md` без `KARTA`, регрессия `git_zona` — все три по-прежнему краснеют); `--no-verify` по-прежнему обходит; коммит, не трогающий инструменты, гейт не будит; линтер по всем инструментам — 0.20 с. Боем НЕ проверено: настоящего чужого коммита через новый гейт ещё не было — первая правка инструмента владельцем и будет проверкой.
