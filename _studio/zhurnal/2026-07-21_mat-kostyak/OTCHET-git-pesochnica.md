---

## 1. Что произошло — в трёх строках

За одну сессию **четыре попытки коммита, три отказа**, все — на канонической форме `add` + `commit -- <пути>`. Причина одна, найдена экспериментом: **песочница Cowork не даёт `unlink` внутри примонтированного репозитория.** Читать и писать можно, удалять — нет.

Pathspec-коммит на этом ломается, потому что он опирается на удаление временного файла. Хуже: каждый упавший коммит **оставляет в `.git/` лок, который сам же снять не может**, и репозиторий встаёт для всех троих писателей — владельца, Cowork и Claude Code.

---

## 2. Проба, воспроизводящая корень (30 секунд)

Из песочницы Cowork, в корне `materials/`:

```
touch /tmp/probe && rm -f /tmp/probe && echo "rc=$?"      →  rc=0        (вне mount — работает)
touch _studio/.probe && rm -f _studio/.probe              →  rm: cannot remove '_studio/.probe':
                                                              Operation not permitted   rc=1
```

Тот же запрет ловится через `.git/`:

```
rm -f .git/index.lock   →  Operation not permitted
```

⚠ Проба **необратима из песочницы**: созданный `_studio/.probe` удалить нечем. Повторять — только на машине владельца или в одноразовом клоне.

---

## 3. Механизм: почему ломается именно pathspec-форма

Канон предписывает два хода: `git add -- <пути>`, затем `git commit -m "…" -- <пути>`. Второй ход — pathspec-коммит — git выполняет через **временный индекс** `.git/next-index-<PID>.lock`: создать → закоммитить → **удалить**. Третий шаг в песочнице невозможен, файл остаётся.

Дальше срабатывает вторая особенность контейнера: **PID крошечные и быстро переиспользуются.** У процесса в этой сессии `pid=5`. Как только новый git получает PID, под которым лок уже лежит:

```
❌ commit упал (rc=128)
   fatal: Unable to create '/…/materials/.git/next-index-15.lock': File exists.
```

Состояние `.git/` к концу сессии — четыре осиротевших лока за полчаса:

```
-rw-------  0       Jul 22 23:03  .git/HEAD.lock
-rw-------  169471  Jul 22 23:30  .git/index.lock
-rw-------  169259  Jul 22 23:03  .git/next-index-15.lock
-rw-------  169259  Jul 22 23:15  .git/next-index-22.lock
```

`index.lock` из этого набора блокирует **любую** запись в репозиторий, кем бы она ни делалась.

**Обычный `git commit` без pathspec `next-index` не создаёт** — то есть ломается не «git в песочнице», а ровно та форма, которую канон сделал обязательной.

## 5. ЦЕНА

- **Репозиторий был заблокирован для всех писателей дважды**, суммарно около получаса. Снять лок из песочницы нельзя — каждый раз требовалось действие владельца в терминале.
- **Владелец получил три подряд отказа на команды, которые я ему выдал как рабочие.** Одна из них (№3) была ошибочной по моей вине, и на её фоне два настоящих дефекта выглядели «опять то же самое» — то есть **шум из-за моей ошибки замаскировал реальную поломку**.
- **Traceback после успешного коммита стоил двух лишних сверок `git log`**, чтобы понять, прошло или нет. Это ровно урок этой арки от 21.07: «код возврата печатать первым — успех и сбой окружения выглядят одинаково». Урок был записан и не помог, потому что здесь его нарушает сам инструмент.
- **`git_zona.py doctor` вызывался при висящем `index.lock` и не сказал о нём ни слова.** Два цикла диагностики прошли вслепую.

## 6. Развилка, которую прошу закрыть в каноне

Сейчас ни `GIT-disciplina.md`, ни контракт зоны в шаблоне захода не отвечают на вопрос: **коммитит ли агент, работающий в песочнице Cowork.** Шаблон говорит «ты работаешь host-side и в `.git` ПИШЕШЬ — значит коммитишь САМ». Для Claude Code это верно, для Cowork-песочницы — нет, и это нигде не оговорено.

Три варианта, как я их вижу. Выбор за аркой.

**(а) Cowork в песочнице не коммитер.** Он правит файлы и сдаёт их строкой «коммита нет, причина такая-то, нужно ваше действие» — форма уже описана в §4 шаблона захода как «внешняя причина». Честно и без мин, но каждый ход аналитика требует терминала владельца.

**(б) Для песочницы прописана другая форма коммита.** `git add -- <пути>` → проверка `git diff --cached --name-only` (в индексе только своё) → **обычный** `commit` без pathspec. `next-index` не создаётся, мин не остаётся. Размен назван честно: pathspec защищал от чужого застейдженного, здесь его заменяет явная проверка списка. Ослабление реальное — в репо трое писателей.

**(в) Уносить временный индекс за пределы mount.** Направление: `GIT_INDEX_FILE` в `/tmp` (там `unlink` работает, проверено в §2). Не проверял, будет ли git класть туда же и `next-index`; если да — самый чистый вариант, если нет — тупик. Проверять надо не в песочнице (см. предупреждение §2).

## 7. Кандидаты в `git_zona.py` — независимо от выбора выше

1. 🔴 **`doctor` обязан показывать локи.** `ls .git/*.lock` с датами первой строкой. Диагност, не видящий самого частого состояния-блокера, отправляет читателя искать причину не там. Оплачено: два цикла вслепую.
2. 🔴 **Уборка не должна убивать процесс после успеха.** `PLAN.unlink()` в `cmd_commit` — в `try/except`, а итоговая строка про хэш печатается ПОСЛЕ уборки, чтобы traceback не приземлялся под словом «✅».
3. **`plan` молча затирает отредактированный черновик.** Повторный вызов возвращает плейсхолдер и стирает уже написанное человеком сообщение. Просится `--force` для перезаписи либо сохранение сообщений, а по умолчанию — отказ, если плейсхолдеров в черновике нет.
4. **Сообщение сейчас вписывается только редактированием файла.** Для агента это лишний ход через `sed`/`python`, на котором я споткнулся дважды. Возможно, стоит `plan --message "…"` для однокоммитного плана. Вкусовое, в отличие от 1–3.
5. **Разовая уборка мин.** После сбоя в `.git/` остаются `next-index-*.lock`; на машине владельца они удаляются, из песочницы — нет. Стоит решить, чинит ли это `doctor` сам (`--fix`, только для файлов старше N минут и только когда git-процессов нет) или это всегда ручной ход владельца.

## 8. Что НЕ прошу и чего не знаю

- **Не прошу трогать саму форму `add` + pathspec для Claude Code.** Она верна, оплачена 21.07 дважды и вне песочницы работает.
- **Не проверял**, воспроизводится ли `next-index`-коллизия при одном коммите за сессию: возможно, редкий агент её никогда не увидит. Число PID-коллизий не мерил.
- **Не проверял** вариант (в) с `GIT_INDEX_FILE` — из песочницы такую проверку делать нельзя, она сама оставит мусор.
- **Не знаю**, ограничение `unlink` — свойство всех песочниц Cowork или конкретно этой сессии/монтирования. Если оно настраиваемое, вся развилка §6 снимается настройкой, и это стоит выяснить первым ходом.
