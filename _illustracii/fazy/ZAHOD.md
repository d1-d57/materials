## 1. ДИСЦИПЛИНА (Карпатов)
- Назови предпосылки ПЕРЕД правкой: какая из 4 веток (`## 3`) на каждый NAME, что уже есть в `tokens.css`, совпадает ли обещание плейсхолдера (N сцен) с `data-scenes`/`data-step-offset` на слайде.
- Минимум без спекуляций: не добавляй сцен/деталей, которых нет в описании и в `data-scenes`; не досочиняй сюжет там, где гибрид-источник не договорил — это вопрос, а не творчество.
- Хирургия: один плейсхолдер → один файл (или одна пара `chapters/+drivers/`) за раз; не переписывай соседние иллюстрации «заодно», даже если стиль кажется улучшаемым.
- Критерий, который может провалиться, — `## 3`.
- Якорные замены: `data-ill`/`data-iframe`, `id` слайда, stem файла — если после замены имя разъехалось с тем, что ждёт слайд, это abort на этом NAME, не переименовывай слайд под свой файл.
- Оспорь ложную предпосылку: плейсхолдер противоречит `data-scenes`/`data-step-offset` слайда или тому, что в гибрид-источнике вообще не описано — стоп на этом NAME, вопрос в `## ВОПРОСЫ`, не гадай молча.
- Предпосылка, которую стоит знать заранее: в проекте пока НЕТ pinned SVGO-конфига с `prefixIds` — per-file id-prefix (критерий `## 3`) на этом заходе делается РУКАМИ, не инструментом.
- Субагенты: плейсхолдеров несколько и они независимы (разные NAME, разные файлы, нет общих зависимостей) → можно параллелить ≤5 за раз, каждому — один NAME + этот файл + его плейсхолдер + его кусок `slides/*`. Рейт-лимит/сбой = отступить и доложить, не слепой ретрай.

## 2. ГРАНИЦЫ

Сохраняй stem/id плейсхолдера ДОСЛОВНО: `data-ill="NAME"`/`data-iframe="tpl-NAME"` в слайде не переписывается; твой файл называется так же, как плейсхолдер (расширение может смениться `.html`→`.svg`, если род оказался вектором, — но убедись, что генератор резолвит именно это имя/расширение, прежде чем удалять старый файл-плейсхолдер). Для ветки 3: номер драйвера (`{{DRIVER:NN}}`) читай ИЗ конкретного `chapters/<NAME>.html`, никогда не угадывай по аналогии с другим чаптером — живой пример разъехавшейся нумерации разобран в `PRIMERY.md` §3.

## 3. ЗАДАЧА
Замени каждый плейсхолдер по правилу оркестрации — 4 ветки (не бинарно SVG/3D):
1. **Статичная схема (линия+заливка, без движения) → локальный `.svg` руками.** Дефолт, ~90% случаев. Канон (`images.md`): тонкая линия 1.5–2.5px, канон-палитра, БЕЗ текста-комментария на картинке — только идентификаторы (`F₁`, `P`, `T`).
2. **Плоский интерактив/анимация (счётчики, броски, drag) → локальный canvas + `lab.js`** (`simulations.md`). НЕ вызывать threejs-скилл для этого — способность специфична презентации (зоны/сцены/dock-панель), пишется на месте, не заимствуется.
3. **По сути 3D-объект (тело, сечение, вращение, вложенные поверхности) → `threejs`.** Строить сцену STANDALONE за render-harness'ем (Playwright+SwiftShader, `window.__shot()`, чек-лист `translucent-depth.md`) ПЕРВОЙ — только потом встраивать в `chapters/<NAME>.html`+`drivers/NN.js`. Антипаттерн, самый дорогой: отлаживать 3D прямо в собранной деке (каждая правка = пересборка колоды, canvas 0×0 пока слайд скрыт).
4. **Готовый растр (график из данных, историческое фото) → код (matplotlib→PNG) или пайплайн `images.md`** (только вайтлист-хосты: Wikimedia/NASA/Met/LoC) → base64 `<img src="data:…">` внутри `illustrations/<NAME>.html`. `<img>`-изоляция здесь ОК — цвет есть содержимое (фото), не тема.

**Критерий ветки 3 одной фразой:** уберём глубину/поворот — картинка перестаёт быть понятной? Да → 3D (ветка 3). Нет → плоский SVG дешевле и надёжнее (ветка 1).

Для ветки 3 — контракт deck↔scene, не своевольничать (полный текст и код — `embedded-scene-in-slides.md`): слайд несёт `data-scenes="N"`+`data-step-offset="K"`; движок шлёт `{goStep:n}`/`{ride:true}` через `postMessage`; глава реализует `goStep(n)`/`resize()`; клик по точке-шагу шлёт `{navSub:n}` РОДИТЕЛЮ (`window.parent.postMessage`), НИКОГДА не дёргает свою навигацию мимо родителя. Строка `<script>window.THREE=window.parent.THREE;<\/script>` рабочая и no-op standalone — не трогать. Число сцен и offset уже известны заранее (из «Вход» в `## 0` или из самого слайда) — строй ровно столько внутренних шагов, либо расщепляй сценарий по `data-step-offset`.

**КРИТЕРИЙ ГОТОВНОСТИ** (условие, способное провалиться — проверяй буквально, не «на глаз»):
- каждый `data-ill="NAME"`/`data-iframe="tpl-NAME"` из «Входа» резолвится в существующий файл `illustrations/NAME.*` или в пару `chapters/NAME.html`+`drivers/NN.js`;
- каждый `var(--x)`, использованный в SVG/canvas, ОПРЕДЕЛЁН в `tokens.css` — непроверенный токен резолвится в чёрную заливку БЕЗ ошибки в консоли: это провал критерия, не мелочь;
- каждый `.svg` несёт `viewBox` + `preserveAspectRatio="xMidYMid meet"` + `width:100%;height:100%;display:block` на корневом `<svg>` (иначе фолбэк на intrinsic-размер и обрезание при масштабе деки — это и ловит `svgOverflow`);
- если SVG заводит локальный `id` (`clipPath`/`gradient`/`mask`/`pattern`) — он несёт per-file префикс по stem файла (руками, см. `## 1`): при инлайне нескольких SVG в один документ два независимых одинаковых `id` тихо ломают друг друга через общий namespace (живой прецедент — `PRIMERY.md` §1в);
- заливки/обводки — ТОЛЬКО токенами `var(--…)` (`--ink --brick --steel --mustard --marker --board --card` и т.п.), НЕ произвольный hex — даже притом что старые эталоны хардкодят hex (см. `PRIMERY.md`), твои НОВЫЕ файлы — через `var()` с первого дня;
- БЕЗ текста-прозы на картинке — только идентификаторы; ни одной фразы-комментария в `<svg><text>` или на canvas;
- `<img>`/base64 — ТОЛЬКО для фото/готового растра (ветка 4); схема, случайно завёрнутая в `<img>` вместо живого `<svg>`, не перекрасится темой и/или даст чёрную заливку;
- ветка 3: сцена прогнана STANDALONE headless (несколько ракурсов) ДО того, как легла в `chapters/*`;
- ни один старый файл-плейсхолдер не остался висеть, если слайд на деле резолвит иное имя/атрибут (живой пример осиротевшего плейсхолдера — `PRIMERY.md` §2) — либо плейсхолдер заменён на месте, либо явно убран/помечен, если род сменился с `data-ill` на `data-iframe` (и наоборот).

Плейсхолдер невозможно закрыть без данных, которых нет (описание неполное, число сцен противоречит слайду, токена нет в `tokens.css`) → НЕ придумывай отсутствующее: стоп на этом NAME, вопрос в `## ВОПРОСЫ`, переходи к следующему. Это честная граница («стоп до цели»), не провал захода — но заяви её громко в `## ОТЧЁТ`.

2. 🔴 **Помарки владельца (`POMARKI-2026-08-09.md §3`)** — `python3 _illustracii/proverka_pomarok.py illustrations/*.svg` (и/или `.html` с инлайн-`<svg>`) на КАЖДОЙ новой/изменённой иллюстрации: П9 (вопросительные знаки запрещены), П12 (фон прозрачный, не белый и не залитый), П10/П11 (равенство композиции не пишется подписью поверх стрелки — рисуется дугой). 3. **Headless-самопроверка, если время и окружение позволяют** — `audit.py` (`svgOverflow`+`svgProse`) на изменённых иллюстрациях. Это частичный самопрогон, НЕ замена финального QA арки 10 — если `audit.py` недоступен/не настроен, не блокируй сдачу, просто зафиксируй в отчёте, прогнал ли.
4. **Ветка 3** — headless-скриншот standalone-сцены с 2–3 ракурсов (`window.__shot()`) ДО встраивания; после встраивания сверься, что `goStep`/`resize` реально переключают шаги (веди навигацию через `location.hash`, не прямым `postMessage` в обход движка).
Это самопроверка автора перед отчётом, не отдельный субагент-верификатор (та методология — для потерь/архивации, здесь не тот случай) — но числа обязаны сойтись: сколько NAME в «Входе» / сколько закрыто / сколько осталось открытыми и почему.
